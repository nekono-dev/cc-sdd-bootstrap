# Implementation Plan

- [ ] 1. 基礎: 純粋な判定を作る（ファイル・時刻・標準入出力を使わない）
- [ ] 1.1 `/kiro-*` の検出と、手順書を読むまでの拒否・記録の判定を作る
  - プロンプトの先頭（前の空白を除く）に置かれた `/kiro-<名前>` だけをコマンドとして取り出す。文中のもの、名前が途切れず別の文字が続くもの、`/kiro-` だけのものは取り出さない
  - コマンド名から手順書の場所を求める。強制の状態（有効か・読むべき手順書・読んだ記録・受けた時刻）を組み立てる。手順書が無くて止めた場合の「無効な状態」も作れる
  - 手順書が未読の間のツール呼び出しを判定する。手順書の Read とツールの検索（ToolSearch）は通し、それ以外は理由つきで拒否する。理由には読むべき手順書のパスを入れる。読んだ後・状態なしは通す。手順書の Read は記録できる
  - 利用者向けの文章を作る: 手順書を先に Read する指示、手順書が無いときの停止の理由（そのコマンドが使えないこと、導入が完了していない可能性、Claude の外で実行する再試行のコマンド。コマンドが渡されないときはその行を省く）
  - 完了の状態: 判定の単体試験が通る（検出の取る・取らない各種、未読での拒否と通す場合、別ファイルの Read の拒否、読んだ後の通過、状態なしの通過、停止の理由の内容）
  - _Boundary: KiroGateRules_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.7, 1.8, 2.1, 2.3, 8.4_

- [ ] 1.2 roadmap の解釈と、ターン終了の判定を作る
  - roadmap の本文から、最後の「Specs (dependency order)」の見出し（水準 2・3）に続く、次の見出しまでの `- [ ]`・`- [x]` の行の spec 名を取り出す。見出しが複数なら最後の節だけを読む。見出し・行が想定の書式でなければ空にする
  - 終了の判定を作る。強制が無効・止めた後の 2 回目以降は通す。手順書が未読なら読むよう求める。読んだ後は、roadmap が直近の `/kiro-*` の後に更新され、一覧の spec に brief.md が無いものがあるときだけ、名前を示して作成を求める。それ以外の状態（承認・チェック）は理由にしない
  - 完了の状態: 判定の単体試験が通る（見出しが複数・水準 2/3・`[x]` を含む・見出しなし・行なし・次の見出しで止まる、未読・brief 欠け・roadmap 未更新・2 回目の通過・状態なし）
  - _Boundary: KiroGateRules_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 4.1, 4.2, 4.3, 4.4_

- [ ] 1.3 セッション開始時の知らせの判定を作る
  - spec ごとに名前・段階・要件／設計／タスクの承認の済・未を 1 行にまとめる。読めない spec は「spec.json を読めない」とし、他の行を妨げない。`.kiro/specs` が無いときはその旨を返す
  - roadmap の有無（ある場合は既存の内容を上書きせず追補する旨）を加えた知らせの文章を作る
  - 完了の状態: 判定の単体試験が通る（承認の済・未の組み合わせ、読めない spec、`.kiro/specs` なし、roadmap の有無）
  - _Boundary: KiroGateRules_
  - _Requirements: 5.1, 5.2, 5.3, 5.4_

- [ ] 2. 入口: 5 つのフックの入出力を作る
- [ ] 2.1 入口の骨組み（入力の読み取り・状態の保存・パスの実体化・失敗時の方針）を作る
  - 起動時の引数でイベントを振り分ける。リポジトリのルートは自分の位置から求め、呼び出し元のカレントに依らない
  - セッションごとの状態を OS の一時ディレクトリに保存・読み取りする。セッション ID の記号は安全な文字に置き換える。状態が無い・壊れているときは「強制なし」として扱う。リポジトリの中には何も作らない
  - 手順書のパスと Read の対象を、フックの入力のカレントを基準に絶対化し、存在すれば実体のパスにそろえて比べられるようにする
  - 入力の JSON が読めないなどの予期しない誤りは、標準エラーに出して何も出力せず終了コード 0 にする
  - 完了の状態: 入口を子のプロセスで動かす試験が通る（壊れた JSON・壊れた状態で出力なし・終了 0、状態がリポジトリの中に作られない、カレントがリポジトリの外でもルートを正しく求める）
  - _Depends: 1.1_
  - _Boundary: KiroGateEntry_
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5_

- [ ] 2.2 プロンプト送信・ツール呼び出しの直前・直後の入口を作る
  - プロンプト送信: 手順書がある `/kiro-*` は状態を保存して先に読む指示を出す。手順書が無いときは無効な状態を保存してプロンプトを止め、再試行のコマンドを導入の失敗の記録の一覧から読んで案内する（読めなければコマンドの行を省く）。`/kiro-` で始まらないプロンプトは状態を解除する
  - ツール呼び出しの直前: 未読の間の拒否を、理由つきの拒否の出力で返す。直後（Read だけ）: 手順書を読んだ記録を状態に足す
  - 完了の状態: 入口の試験が通る（手順書あり・なし・始まらないプロンプトの出力、未読の Bash の拒否、手順書の Read の通過と記録、相対パス・シンボリックリンク経由の Read でも記録が付く、続けて別の `/kiro-*` を送ると最新の手順書だけを要求する）
  - _Depends: 2.1, 1.1_
  - _Boundary: KiroGateEntry_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7, 2.1, 2.2, 2.3, 8.4_

- [ ] 2.3 ターン終了とセッション開始の入口を作る
  - ターン終了: roadmap の本文と更新時刻、一覧の spec のうち brief.md があるものの名前を集めて判定に渡し、止めるなら理由つきの出力を返す。止めた後の 2 回目の入力（`stop_hook_active` が真）は通す
  - セッション開始: `.kiro/specs` の下の spec.json を集める。spec.json が無いディレクトリは対象にしない。読めない・不正な JSON は「読めない」として判定に渡す。知らせを文脈に入る出力で返す
  - 完了の状態: 入口の試験が通る（未読で止める、roadmap を更新して brief が欠けた spec があると止め 2 回目は通る、brief が揃っていれば通る、roadmap 未更新・強制なしで通る、セッション開始の知らせの内容、spec.json の無いディレクトリを含めない）
  - _Depends: 2.2, 1.2, 1.3_
  - _Boundary: KiroGateEntry_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 5.1, 5.2, 5.3, 5.4, 5.5_

- [ ] 3. 配布: カタログに載せる
- [ ] 3.1 配置するファイル・フック・CLAUDE.md の節をカタログに足す
  - 配置するファイルに 2 件を足し、パッケージの配布対象にも登録する
  - フック 5 件（セッション開始・プロンプト送信・ツール呼び出しの直前・直後・ターン終了）を既存のものの後ろに足す。直後だけ Read に絞る（matcher）。時間制限は各 10 秒
  - CLAUDE.md の管理区画に、`/kiro-*` で始めた作業の強制と brief.md の欠けの説明、承認済みの 7 行の対応表（依頼の種類とスキルの対応）、SKILL.md を Read して手順を最後まで実行すること、判断できないときは利用者に尋ねることを書いた節を足す
  - 完了の状態: カタログの試験とパッケージの試験が通る（ファイルとフックの内容、直後だけ matcher あり、節に 7 つのスキル名と Read の指示が含まれる、配布対象に 2 件が載る）
  - _Depends: 2.3_
  - _Boundary: Catalog_
  - _Requirements: 7.1, 7.5, 8.1, 8.2, 8.3_

- [ ] 4. 統合: 導入・更新・取り除きと自己適用
- [ ] 4.1 導入・更新・取り除きの通しの試験に kiro-gate を足す
  - 利用者が書いたフックと session-install のフックがある導入先で、`init`・`update` が kiro-gate のフックを足したまま既存のフックを残すことを確かめる
  - `update` でファイルとフックの登録・CLAUDE.md の対応表が、このリポジトリの内容に揃うことを確かめる。`uninstall` で kiro-gate の分（ファイル・フック・対応表）だけが消え、利用者のフックが残ることを確かめる
  - 完了の状態: 通しの試験が通り、導入・更新・取り除きの各場面で上の内容が確かめられる
  - _Depends: 3.1_
  - _Boundary: Integration（導入コマンドの通しの試験）_
  - _Requirements: 7.2, 7.3, 7.4, 8.5, 8.6_

- [ ] 4.2 このリポジトリへ自己適用し、全体の試験を通す
  - 導入コマンドの更新を実行し、フックの登録・CLAUDE.md の管理区画・配置の記録が更新されることを確かめて、結果を取り込む
  - 全体の試験（`npm test`）を通す
  - 完了の状態: 登録にフック 5 件が増え、管理区画に対応表が入り、全体の試験が通る。更新をもう一度実行しても差分が出ない
  - _Depends: 4.1_
  - _Boundary: Integration（このリポジトリへの適用）_
  - _Requirements: 7.1, 7.3_

  - 完了の状態: PoC を再実行でき、すべて OK になり、結果の文書が実物の確認の内容に更新されている
  - _Depends: 4.2_
