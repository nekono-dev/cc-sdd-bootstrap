# Implementation Plan

> 順序の方針: 実機検証が必要な spec のため、最初のタスク群（1）で、純粋部品・版の取り出し・入口・カタログ登録と計画への記録を最小の形で通し、実際の `npx`・`claude`・`codex` で確かめる（1.7）。確かめられなければ以降に進まず設計へ戻す。`lib/catalog.mjs`・`package.json` を触るのは 1.6 だけにする（入口の本体は 1.5 で先に作り、カタログへの登録は 1.6 でまとめて行う）。

- [ ] 1. 記録と照合を端から端まで動かす（最小の形と実機の確認）
- [x] 1.1 記録の形・分類・照合を作る（純粋な部品の前半）
  - 配置物ファイルごとの指紋と配布元の版を、決まった並びの記録の文字列にする処理と、読み取った記録を「無い・壊れている・正常」に分ける処理を作る
  - 記録と実際のファイルの指紋から、欠けているもの・内容が違うものを分ける
  - 単体試験で、同じ入力から同じ記録になること、記録の分類（無い・壊れている・形式違い・指紋が不正・正常）、欠け・違い・一致の判定が確かめられる
  - _Boundary: FreshnessRules_
  - _Requirements: 1.1, 1.3, 2.1, 2.2, 2.3, 2.4, 2.6, 5.1, 5.2_
- [ ] 1.2 最新との比較・更新コマンド・案内の判断と文面を作る（純粋な部品の後半）
  - 配布元の最新と記録の版を比べ、同じ・古い・不明に分ける（版が不明・取得できない・取得時の指定が固定のコミットは不明）
  - 配布元への問い合わせの指定（取得時の指定がブランチ・タグならその先頭、指定が無ければ既定の先頭）と、取得した出力からコミットを選ぶ処理を作る（注釈つきタグの「タグ本体と `^{}` の指す先の組」は許容して指す先を選ぶ。それ以外の曖昧な複数候補・不正な出力は使わず、不明とする。40 桁の 16 進だけを取り出す）
  - 更新コマンド（取得時の指定があれば付ける。固定のコミットは付けない）と、案内の有無の判断・文面を作る。内容の違いを編集と断定せず、版が不明の旨は他の案内があるときだけ添える。最新との比較が不明でも、照合の結果があれば案内する。記録が無い・壊れている場合の文面に、古い導入には検知の仕組みが無く初回は手で更新する旨を入れる。案内は利用者向けの 1 文と、エージェントへ「回答より前にそのまま出力する」指示の両方を返す
  - 単体試験で、最新の比較と問い合わせの指定・出力の選び方（ブランチ・注釈つきタグ・軽いタグ・既定・固定・複数行・不正）の全ての分岐と、案内の有無・文面（更新コマンドを含む、断定しない、版不明の添え方、最新が不明でも照合の結果は案内）が確かめられる
  - _Depends: 1.1_
  - _Boundary: FreshnessRules_
  - _Requirements: 2.5, 3.1, 3.2, 3.4, 3.6, 4.1, 5.1, 5.2, 5.5_
- [ ] 1.3 (P) 配布物の位置から配布元のコミットと取得時の指定を取り出す
  - 配布物の親が `node_modules` のときだけ、1 つ上の `.package-lock.json` から 40 桁のコミットを、2 つ上の `package-lock.json` から取得時の `#` 以降を取り出す。形が違う・読めない・`node_modules` の下でないときは、例外にせず「取り出せなかった」を返す
  - 所有するのは、配布元の版の取り出しの部品と、その専用の試験だけ。共通の試験用の受け皿は変えない（変えるのは 1.4）。導入コマンドの読み取りへの接続は 1.6 が行う
  - 単体試験で、擬似の配置からコミットと指定を取り出せること、指定が無い・形が違う・手元の checkout の位置では取り出せないことが確かめられる
  - _Boundary: SourceReader_
  - _Requirements: 1.3, 1.4_
- [ ] 1.4 入口の試験用の受け皿を一般化する
  - 既存の試験用の受け皿（`test/helpers/entry-harness.mjs`）は、起動する入口とコピーする配置物が `install-cc-sdd.mjs` に固定されている。起動する入口と配置物の一覧を指定できるようにし、既存の試験の挙動は変えない
  - カタログに登録する前でも、指定した入口と配置物のファイルを一時のリポジトリへ直接コピーして起動できる。このタスクの検証には、試験専用の仮の入口と配置物（本物の入口は 1.5 で作る）を使う
  - 既存の入口の試験が全て通り、試験専用の仮の入口を指定して一時のリポジトリで起動できる。本物の入口の検証は 1.5 が行う
  - _Boundary: Test harness_
  - _Requirements: 4.5_
- [ ] 1.5 セッション開始の入口を作る
  - 自分の位置から導入先のルートを求め、記録を読み、記録の各ファイルの指紋を求めて照合する。記録に版があり固定でないときは、配布元の最新を認証の入力を求めない設定・待ち時間 3 秒で取得して比べる。案内があるときだけ、標準出力へ 1 行の JSON を出す。形は、利用者向けの表示欄 `systemMessage`（利用者向けの案内文）と、`hookSpecificOutput`（`hookEventName` が `SessionStart`、`additionalContext` にエージェントへ「回答より前にそのまま出力する」指示と案内文）。案内が無いときは何も出さない
  - 記録のファイルが無いことと、それ以外の読み取り失敗・不正な形式を分けて案内へ渡す。通信の失敗・待ち時間の超過では、最新との比較だけを省き、照合の結果は案内する。それ以外の想定外の失敗・対応外の引数では、何も出さずに終了コード 0 で通す。入力の拒否・停止の出力を一切持たない
  - 試験は 1.4 で一般化した受け皿を使う
  - 標準入力・擬似の記録・擬似の `git` を使う試験で、一致なら出力なし、欠け・違い・記録なし・壊れ・最新との差で案内、通信の失敗でも照合は案内、想定外の失敗・対応外の引数でも出力なしで終了コード 0、両ツールで同じ形になること、出力の各欄（`systemMessage`・`hookEventName`・`additionalContext`）の値と、利用者向けの文面・エージェントへの指示がそれぞれ含まれること、問い合わせに認証の入力を求めない設定が渡ることが確かめられる
  - _Depends: 1.2, 1.4_
  - _Boundary: FreshnessEntry_
  - _Requirements: 2.1, 2.2, 2.6, 3.1, 3.3, 3.4, 3.5, 4.1, 4.3, 4.4, 4.6, 5.1, 5.2, 5.3, 5.4_
- [ ] 1.6 カタログ・配る範囲への登録と、導入・更新の計画への記録の追加を行う（統合）
  - カタログの配置物に入口と純粋部品を、フックに Claude Code・Codex のセッション開始の登録（セッション開始にだけ。タイムアウトは両ツールとも 10 秒）を足し、配る範囲にも足す。記録は配布物に含めない
  - 読み取りに配布元の版（1.3）を足し、計画で、配置物と運用の区画の 2 ファイルの指紋と配布元の版から記録を作り、配置ディレクトリの書き込みの最後に足す。記録自身は記録に含めず、配置ディレクトリの削除対象から外し、uninstall では触らない。同じ内容なら変更なしになる
  - 単体試験で、init・update の計画に記録が入ること、記録のキーが配置物（入口・純粋部品を含む）と運用の区画のファイル集合と一致すること、同梱の内容が変わると指紋が変わり、変わらなければ変更なしになること、フックの登録が両ツールのセッション開始にだけあり、タイムアウトが 10 秒であること、uninstall では記録に触らないことが確かめられる
  - _Depends: 1.1, 1.2, 1.3, 1.5_
  - _Boundary: InstallerIntegration_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 4.2, 4.5_
- [ ] 1.7 実機で、記録の書き込みと案内を端から端まで確かめる
  - 事前条件（満たせなければ開始せず、未確認として停止し、利用者へ報告する）: 認証済みの `claude`・`codex`、GitHub への通信、作業ブランチへ push できること。1.1〜1.6 をコミットして作業ブランチへ push し、そのコミットを検証の対象として結果に記録する
  - 必須の確認（1 つでも成立しなければ以降に進まない。実装・設計の前提が実機で成立しないときは設計へ戻し、認証切れ・通信障害など環境の理由で観測できないときは、未確認として停止して利用者へ報告する）: ① 一時のリポジトリで実際の `npx github:…#<作業ブランチ> init`・`update` を行い、記録のコミットが配布元のブランチの先頭と一致する。② 一致の状態を基準に、各異常を個別に作って（記録のコミットを古い値にする／ファイルを 1 つ書き換える／別のファイルを 1 つ消す）、場面ごとに一致の状態へ戻し、実際の `claude -p`・`codex exec` のセッション開始で、それぞれ最新との差・内容の違い・欠けの案内の文脈が届く。複合の状態は必須にしない。③ 全て一致のときは何も出ない。④ 記録を消すと記録なしの案内が出る
  - 観測として記録するだけで、進行の条件にしない項目: 利用者への伝達の有無。確かめられない項目は未確認として結果に残す
  - 実行の形: 検証対象のコミットと作業ブランチ名を結果に記し、導入先は使い捨ての一時のリポジトリにして、終了後に消す。`poc/install-freshness/` に場面を足し、結果を `result.md` に追記する
