# Brief: install-freshness

## Problem
cc-sdd-bootstrap を導入した利用先（例: branch-release-workflow のリポジトリ）が、導入時の古い配置物（`.agent-hooks/cc-sdd-bootstrap/` と設定）のまま使われ続けても、誰も気づけない。2026-11-26 に、work-branch-flow を足す前のコピーが残っていたため、`main` の上で `/kiro-discovery` が始まり、作業ブランチが切られなかった。

## Current State
- セッション開始時の導入（session-install）は「cc-sdd の導入物が揃っていれば入れ直しを省く」だけで、cc-sdd-bootstrap 自身の配置物が古いかは見ない。
- `package.json` の版（`0.1.0`）は機能が増えても変わらず、版の違いで古さを判定できない。
- 配置物の導入元（版・コミット）の記録が無い。単純化（2026-11-22）で「配置したファイルの記録と改変の検出」は外した。
- `npx` のキャッシュに古い版が残っていると、`update` しても古い配置物が書かれる可能性がある（未確認）。

## Desired Outcome
- 導入・更新のとき、配布元の版（コミットなど）と配置物の内容の指紋を記録する。
- セッション開始時に、記録と実際の配置物のずれ（欠けている・古い・内容が違う）、または配布元の新しい版との差を検知し、短い案内（更新コマンド）を出す。
- 検知は案内までで、自動更新はしない。判定できないとき（通信できない・記録が無い）は止めず通す。

## Approach
利用者が選んだ「版の記録とずれの案内」。導入時に記録を書き、セッション開始のフックで読み比べて案内する。自動更新（通信と書き換えが毎回の開始に入る）と、運用だけで済ます案（検知できない）は退けた。

## Scope
- **In**: 導入・更新時の記録（版・コミット・内容の指紋）の書き込み、セッション開始時の照合と案内、更新コマンドの案内、記録が無い古い導入（今回の事故の状態）の扱い、PoC（`npx` のキャッシュの影響・配布元の最新を安く確かめる方法）。
- **Out**: 自動更新、cc-sdd 本体の導入物の検査（session-install の範囲）、利用者が配置物を編集したかどうかの追及（改変の検出は目的にしない）、worktree 導入の案内文面（直接実装 worktree-install-guide）、Codex の表示文面（直接実装 codex-readonly-notice）。

## Boundary Candidates
- 記録の形と書き込み（導入コマンド側）
- セッション開始時の照合と案内（配置物側の新しい関門、または session-install の既存フックへの追加）
- 配布元の最新との比較（通信を伴うか。伴うなら失敗時は通す）

## Out of Boundary
- 古いコピーを直接直す仕組み（古いコピーには検知の仕組みが無いので、初回は手で `update` する前提）。
- 通信が使えない環境での最新の判定。

## Upstream / Downstream
- **Upstream**: installer-core（導入・更新の計画と書き込み、設定ファイル）、session-install（セッション開始時のフック・導入状態の案内）。
- **Downstream**: 利用先すべて。ほかの関門（work-branch-flow など）が確実に最新の配置物で動く前提になる。

## Existing Spec Touchpoints
- **Extends**: installer-core（記録の書き込みを導入・更新に足す）、session-install（セッション開始時の案内に足すか、新しい関門にするかを設計で決める）。
- **Adjacent**: work-branch-flow（古い配置物のせいで関門が動かなかった当事者）、codex-hook-trust（導入・更新の行程で同じように記録を書く）。

## Constraints
- Node.js 22 以上、外部パッケージなし。厳密さのためにコードを増やさない。
- フックは「判定できないときは通す」。止めるのは案内だけで、入力は止めない。
- 記録に配布元の版（コミット）を入れるには、`npx` で取得した配布物から版を取り出せるかを PoC で確かめる（根拠は一次資料か再実行できる PoC）。
- 古さの判定は、古いコピーでは動かない（検知の仕組みが入っていない）ので、将来のずれに対してだけ有効である点を要件に明記する。
- 要確認（要件段階）: 「配布元の新しい版との差」の判定に通信を使うか、設定ファイルに期待する版を持たせるか。単純化の方針（改変の検出は目的にしない）との境界を、指紋は「欠け・混在の検知」に限ると決めるか。
