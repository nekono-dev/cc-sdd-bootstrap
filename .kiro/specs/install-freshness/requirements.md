# 要件文書

## Project Description (Input)

**対象の利用者**: cc-sdd-bootstrap を導入したリポジトリで、Claude Code または Codex を指揮役として開発する人。branch-release-workflow など、別の開発手順を重ねたリポジトリを含む。

**解決する問題**: 導入先の配置物（`.agent-hooks/cc-sdd-bootstrap/` と設定）が導入時の古いコピーのまま使われ続けても、誰も気づけない。2026-11-26 に、work-branch-flow を足す前のコピーが残っていたため、`main` の上で `/kiro-discovery` が始まり、作業ブランチが切られなかった。現状は、セッション開始時の導入が cc-sdd の導入物の有無しか見ず、配布物の版（`package.json` の `0.1.0`）は機能が増えても変わらず、配置物の導入元の記録も無い。

**実現すること**:
- 導入・更新のとき、配布元の版（コミット）と配置物ごとの内容の指紋（内容から計算した短い識別値）を記録する。
- セッション開始時に、記録と実際の配置物のずれ（欠け・混在）と、配布元の最新との差を検知し、更新コマンドを短く案内する。
- 検知は案内までとし、自動更新はしない。判定できないときは止めずに通す。

**利用者が決めたこと（2026-11-26）**: 配布元の最新との差は通信して調べる。指紋は欠け・混在の検知だけに使い、利用者が配置物を編集したかの追及はしない。案内はセッション開始時だけ出す。

## Introduction

本仕様は、導入先の配置物が古い・欠けている・版が混ざっていることを、セッション開始時に利用者へ知らせる「導入の鮮度の検知」の振る舞いを定める。導入・更新のときの記録、セッション開始時の照合、配布元の最新との比較、案内の内容を対象とする。入力を止めることや自動更新は行わない。

## Boundary Context

- **In scope**: 導入・更新時の記録（版・コミット・内容の指紋）の書き込み、セッション開始時の記録と配置物の照合、配布元の最新との比較、更新コマンドの案内、記録が無い導入の扱い、判定できないときの通し方。
- **Out of scope**: 自動更新、cc-sdd 本体の導入物の検査（session-install の範囲）、利用者が配置物を編集したかどうかの追及、フックの登録や運用の区画の文章の欠けの検査、worktree 導入の案内文面、Codex の読み取り専用の子の表示文面、通信できない環境での最新の判定。
- **Adjacent expectations**:
  - installer-core: 導入・更新の行程で、記録を書き込む。配置するファイルの一覧は installer-core が決めたものを使う。
  - session-install: セッション開始時のフックの仕組みを使う。導入未完了で入力を止める働きは変えない。本仕様の案内は入力を止めない。
  - codex-hook-trust: 導入・更新の行程で、同じように記録を書く点が隣接する。承認の記録の仕組みは変えない。
  - 古いコピー（本仕様の導入前の配置物）は検知の仕組みを持たないため、本仕様は将来のずれに対してだけ働く。初回は利用者が手で更新する前提である。

## Requirements

### Requirement 1: 導入・更新のときの記録

**目的:** 導入先の管理者として、配置物がどの版から導入されたかを後から確かめたい。

#### 受け入れ基準

1. When 導入コマンドが配置物を導入先へ書き込む, the 導入コマンド shall 配布元の版（コミット）と、配置したファイルごとの内容の指紋を、導入先のファイルへ記録する。
2. When 導入コマンドが更新として実行される, the 導入コマンド shall 記録を、更新後に実際に配置した配置物の版と指紋で置き換える。
3. The 導入コマンド shall 記録の版を、配置した配布物から取り出せた実際の版とし、取り出せないときは「版を取り出せなかった」ことを記録へ明示する。
4. If 配置した配布物が古い版のままで、配布元の最新と異なる, then the 導入コマンド shall 最新と偽らず、実際に配置した版を記録する。
5. If 記録の書き込みに失敗する, then the 導入コマンド shall 失敗を利用者へ示し、記録の無い状態を成功として扱わない。

### Requirement 2: セッション開始時の記録と配置物の照合

**目的:** 開発者として、配置物の欠けや版の混在を、作業を始める前に知りたい。

#### 受け入れ基準

1. When セッションが開始される, the 鮮度の検知 shall 記録に載っている各ファイルが導入先に存在するかを確かめる。
2. When セッションが開始される, the 鮮度の検知 shall 存在する各ファイルの内容の指紋を、記録の指紋と比べる。
3. If 記録に載っているファイルが導入先に無い, then the 鮮度の検知 shall そのファイルを「欠けている」ものとして案内に含める。
4. If 記録の指紋と一致しないファイルがある, then the 鮮度の検知 shall そのファイルを「記録と内容が違う」ものとして案内に含める。
5. The 鮮度の検知 shall 内容が違うファイルを、利用者が編集したものとは断定せず、版の混在や不完全な更新の可能性として案内する。
6. While 記録と全ファイルが一致している, the 鮮度の検知 shall 照合の結果について案内を出さない。

### Requirement 3: 配布元の最新との比較

**目的:** 開発者として、配置物が配布元の最新より古いときに気づきたい。

#### 受け入れ基準

1. When セッションが開始され、記録に版（コミット）がある, the 鮮度の検知 shall 通信して配布元の最新の版を取得し、記録の版と比べる。
2. If 記録の版が配布元の最新と異なる, then the 鮮度の検知 shall 配置物が最新と異なることを案内に含める。
3. If 通信できない・応答が無い・待ち時間を超えるなど、最新の版を取得できない, then the 鮮度の検知 shall 最新との比較を省き、そのことを理由にセッションの開始を止めない。
4. If 最新の版を取得できなかった, then the 鮮度の検知 shall 記録と配置物の照合の結果（要件 2）は引き続き案内する。
5. The 鮮度の検知 shall 通信の待ち時間に上限を設け、セッションの開始を遅らせすぎない。
6. If 記録の版が「版を取り出せなかった」である, then the 鮮度の検知 shall 最新との比較を行わず、その旨を案内に含める。

### Requirement 4: 更新の案内

**目的:** 開発者として、ずれに気づいたときに、何をすればよいかをすぐ知りたい。

#### 受け入れ基準

1. When 欠け・内容の違い・最新との差のいずれかを検知した, the 鮮度の検知 shall 検知した内容の要点と、更新に使うコマンドを短く案内する。
2. The 鮮度の検知 shall 案内を、セッション開始時にだけ出す。
3. The 鮮度の検知 shall 案内を出しても、利用者の入力・作業を止めない。
4. The 鮮度の検知 shall 配置物を自動で更新・書き換えしない。
5. The 鮮度の検知 shall 案内を Claude Code と Codex の両方のセッション開始時に利用者へ届ける。
6. If 欠け・内容の違い・最新との差のどれも検知しなかった, then the 鮮度の検知 shall 何も案内しない。

### Requirement 5: 記録が無い導入と判定できないときの扱い

**目的:** 開発者として、検知の仕組みが入る前の古い導入や、判定できない状況でも、作業を妨げられたくない。

#### 受け入れ基準

1. If 導入先に記録が無い, then the 鮮度の検知 shall 「導入の記録が無く、鮮度を確かめられない」ことと更新コマンドを案内する。
2. If 記録が読めない・形式が想定と違う, then the 鮮度の検知 shall 記録が壊れている可能性と更新コマンドを案内し、セッションの開始を止めない。
3. If 照合や比較の途中で想定外の失敗が起きる, then the 鮮度の検知 shall セッションの開始を止めずに通す。
4. The 鮮度の検知 shall 記録が無い、または読めないことを、理由なく利用者の作業の拒否に使わない。
5. The 導入先向けの案内文書 shall 本仕様の導入前の配置物には検知の仕組みが無く、初回は利用者が手で更新する必要があることを明記する。
