# Research & Design Decisions

## Summary

- **Feature** — `codex-delegation`
- **Discovery Scope** — 利用者が登録済みの MCP を探査し、既存の役割契約と組み合わせて委任する複合連携。
- **Key Findings** — Pi MCP はモデル一覧と役割ごとの権限を判定できる。Codex の既存 MCP はモデル・状態の公開契約の追加が必要。ホストによって登録の形式と承認方法が異なる。

## Research Log

### MCP の探査とホストの承認

- MCP の `initialize` と `tools/list` でサーバー情報と公開ツールのスキーマを得られる。仕様には汎用のエージェント型・実行形態・モデル一覧を示すフィールドがない。確認済みの接続契約で能力を正規化する。
- Codex CLI の `mcp list --json` で有効な `pi-agent` と stdio 登録を取得した。Claude Code は `mcp list` と `mcp get` がプロジェクト承認を反映し、Pi は `mcp list --json` と信頼済みプロジェクトの登録を提供する。これらの仕様を登録解決に利用する。
- Pi と Claude Code の一覧コマンドはホストの規則に沿って有効なサーバーの状態も確認する。Claude Code による承認待ちのプロジェクト MCP を独自に起動する理由にはしない。stdin やシェルへの登録値の連結、認証情報の出力は避ける。
- Muse の登録列挙・ネイティブ起動はこの環境で未検証。クラウド型 Codex の系統除外は指揮役が Claude Code かどうかに依存させず、登録解決が確認できたハーネスを同じ契約に接続する。

### Claude Code の管理対象登録

- プロジェクト登録を使う理由は、リポジトリを導入した利用者が同じ管理エントリを見られ、承認は引き続きホストに任せられるため。既存の skyshare は `git rev-parse --show-toplevel` で配置先を解決する。これと同じ方法を管理対象の固定ランチャーに適用し、端末の絶対パスを保存しない。
- 設定へ書いた時点では登録は予定または承認待ちであり、認可された実行先と区別する。Claude Code の別スコープ優先と、承認待ち・無効状態を登録の解決時に尊重する。一時リポジトリで管理名が承認待ちとして表示され、未起動であることを確認した。固定ランチャーは空白を含むリポジトリのサブディレクトリからもルートで動いた。

### 既設の Pi MCP

- このセッションの `pi_capabilities` はエージェント型・Pi・ローカルと、`read-only`、`workspace-write`、`off` を公開した。`pi_models` は構造化応答に受付モデル ID 6 件を返した。モデル名の一覧が変わっても、推論量が役割条件に合わなければ選ばない。
- 既設の `pi_start`、`pi_status`、`pi_cancel` は同じ stdio 接続に結び付いたジョブを扱う。接続を失った場合に同じジョブ ID を新しいプロセスで見つけられないことがあり、実行済みか不明の書き込みを次の候補で始める根拠にはできない。
- 先行検証で、読み取り専用のツール制限と作業先のファイルシステム制限を実機で確認した。今回の探査は能力と一覧の確認に限定した。

### Codex MCP と役割契約

- skyshare の `codex_exec` は実行側で権限を指定し、作業先と実行時間を検査する。公開ツールの説明には既定モデルがあり、読み取り専用の推論量は固定されている。今回の条件では、モデル候補と実行可能な組み合わせを機械的に公開し、明示のモデルと推論量で起動する必要がある。
- 認証情報を含まない一時設定で実物の Codex app-server に `model/list` を送り、9 件を取得した。Luna と Sol の双方について `medium` と `high` を取得できた。カタログは利用権や稼働状態を表さない。Codex MCP が CLI の受付範囲を公開し、委任側はその公開結果を使う。
- subagent-model-policy が役割ごとの権限、推論量、ローカル候補 ID とネイティブ定義を提供する。installer-core の `clients` と `codex.enabled` は独立しており、後者の既存値を段順やクライアント種別の代わりに用いない。

## Design Decisions

| 比較した方法 | 採用判断 |
|---|---|
| MCP の名前から機能を推定する／公開された契約を照合する | 公開契約を照合し、候補・系統・受付モデル・権限を共通の形に変換する。 |
| cc-sdd の手順の度に指揮役へ選択を指示する／共通の実行入口に規則を持つ | 優先順と不明時の切り替えを一か所で機械判定する。管理区画からこの入口を使い、ネイティブ起動は対応クライアントと上流ガードに任せる。 |
| 既存の同期呼び出しをそのまま採用する／状態・停止を公開する | 起動前の不成立と起動後の不明を区別できる契約を追加する。CLI 呼び出しや実行権限の処理は既存の方式を利用する。 |

## 接続所有の改訂判断

- 2026-11-21 の確認で、接続は依頼ごとの一時プロセスが持つと決定した。プロジェクト常駐方式なら複数依頼をまとめて管理できるが、常駐プロセスの監視・更新が加わる。依頼単位のプロセスで状態と停止を同じ MCP 接続へ届け、所有者が失われたときは書き込みを自動再送しない。模擬 stdio で、起動・状態確認・停止を別プロセスからファイル経由で同じ所有者に送り、同一の stdio 子プロセスが応答することを確認した。
- サーバーのジョブ ID は接続やサーバープロセスが変わっても使える識別子とは限らない。管理側では呼び出しごとの依頼 ID と、異なる依頼 ID で同じ作業が再送されたことを識別するキーを持つ。

## Risks & Mitigations

- 接続・起動が不明な書き込み依頼は、同じ依頼 ID で確認できる状態を残す。状態取得不能を停止済みと扱わない。
- 同じ表示名で MCP が差し替わる場合に備えて、登録先を再照合する。動的なモデル一覧と登録設定の変更を区別する。
- 現行 Pi MCP は `off` のみ。役割側の推論量を維持し、該当するモデルがなければ次の段へ進む。
- 対応未確認のホストの設定手順を名前から推測しない。利用できる登録の列挙・承認の確認・ネイティブ起動を対象ホストで確認する。

# ギャップ分析（2026-11-22・実装 2.1〜5.3 と実機検証 6.1・6.2 の後）

## 分析の要約

- 要件 1〜5 は、部品単位ではほぼ実装済みで、単体・結合テスト（626 件、既存の無関係な 3 件を除く）も通っている。
- ただし実機では、**管理入口を通る一本の経路がまだ成立していない**。原因は次の 3 点。(G1) 管理入口の呼び出し参照がモデルへ届かない。(G2) 実際の Pi の能力応答の形と、接続部品が要求する形が合わない。(G3) ネイティブだけの構成で、単独の事前確認が拒否される。

- 管理委任（直接起動の拒否）は、両クライアントで無効のまま。G1 が解けるまで有効化できない。

## 3. ギャップと選択肢

### G1（重大）管理入口の呼び出し参照がモデルに届かない

- 事実: `delegate.mjs start` は `--reference` が必須。参照は上流のフックが `enter` の Bash 命令に付け足す仕組みだが、`enter` の出力には参照が含まれず、モデルが `delegate.mjs start` に渡せない。拒否文は「`enter` で発行された参照を渡す」と案内しており、有効化すると行き止まりになる。
- 選択肢:
  - **A**: `enter` の出力に参照を載せる。簡単だが、参照（一回限りの秘密）がモデルの文脈とログに残る。
  - **B（推奨）**: `delegate.mjs start|status|stop` の Bash 呼び出しを、上流フックが `enter` と同じ方法で書き換え、参照を付け足す（`updatedInput`）。参照はモデルに渡らず、既存の仕組みと一致する。Codex 側は同等の書き換えが可能かを要確認。
  - **C**: 参照なしで、フックが書いた作業コンテキストのファイルから入口が解決する。参照の消費による偽装防止が弱まる。
- 要確認（Research Needed）: Codex のフックが Bash の入力を書き換えられるか。

### G2（重大）Pi の能力応答の形が合わない

- 事実: 実際の Pi は `execution`・`access_modes`・`thinking_levels` を返す。`createPiAdapter` は `tier` と `models[].accepted` を要求し、実登録は必ず不適格になる。設計メモ（既設の JSON テキスト形式の能力を正規化する）とも食い違う。
- 選択肢: **A（推奨）** 接続部品側で実際の形を正規化して共通の `Capability` に変換する（モデル一覧は `pi_models` と組み合わせ、権限×推論量の組は公開された集合の直積とみなせるか要確認）。**B** Pi 側（`pi_mcp.py`）を変更する。リポジトリ外のため非推奨。

### G3 ネイティブ単独の事前確認が常に拒否される

- 事実: 導入台帳に `delegate.mjs` が載るだけで「外部委任の配置あり」と判定される。外部 MCP を置かない構成でも同じ。
- 選択肢: 判定を、実際に有効な外部候補の有無（設定の候補）に基づける（推奨）／判定を台帳ではなく管理委任の有効状態に結び付ける。

### G4 Pi の登録一覧の形が未確認

- 事実: `pi mcp list --json` の外側は `{servers, errors}` までしか確認できていない（この環境では登録が空）。承認状態が null のため Pi は eligible にならない。
- 要確認: 登録済みの Pi で一覧の項目の形（信頼済みプロジェクトの扱い）を実測する。

### G5 Codex クライアントの実機確認が未実施

- 未確認: Codex の PreToolUse での MCP 起動の検出・拒否、MCP ツール名の形（`mcp__<サーバー>__<操作>` と仮定）、Codex MCP の実機起動。2026-11-27 以降に実施する。

### G6〜G13（中・低）

- G6 管理委任が無効のまま（G1 の解決後、実機確認を経て有効化）。
- G7 系統を保存値で照合している。MCP が公開する `harness` との突き合わせを入れるか（設計の「承認済み候補について能力を調べる」と整合）。
- G8 ガードの照合が設計（登録名・スコープと操作名）より広い（安全側）。有効化時に範囲を確定する。
- G9 transport の読み直しは Claude の project `.mcp.json` が中心。ほかのホスト・スコープは「確認不能」と表示して選べない。
- G10 状態確認・停止にセッション単位の所有者確認が無い（作業ツリーと記録で照合）。
- G11 部分書き込みが未確認。G12 ネイティブで任せた書き込みは依頼記録に残らない（上流の追跡）。G13 停止要求前に本体が終了して子孫が残る場合は未対応。
- 既存の無関係な失敗 3 件（subagent-model-policy の Claude 起動テスト）。

## 4. 実装の進め方の選択肢

- **A: 既存部品の拡張**（推奨）。G2 は `delegation-mcp.mjs`、G3 は上流の事前確認の判定、G1 は上流の `kiro-delegation-context.mjs`・フックの拡張。新規ファイルは不要。上流（subagent-model-policy）の部品を触るため、所有仕様の再検証が要る（再検証の引き金に該当）。
- **B: 管理入口に参照の取り扱いを閉じ込める新部品**。上流を変えずに済むが、参照の消費という上流の保証を二重に持つことになり、整合の維持が重い。
- **C: ハイブリッド**。G2・G3 は A、G1 は上流の仕様を先に改訂（subagent-model-policy に参照の受け渡しを足す）してから実装する。順序が最も安全。

努力の目安: G2・G3 は小（各 1 日以内）。G1 は中（上流の改訂を含む 2〜3 日）。リスクは G1 が高（上流との整合、Codex のフックの書き換え可否が未確認）。

## 5. 次の段階への申し送り

1. G1 の選択肢（B 推奨）を決める。決定が上流の契約を変えるため、subagent-model-policy への影響（Revalidation Triggers）を先に確認する。
2. G2・G3 は設計の範囲内の不具合修正として、タスク 3.1・5.2 の再オープンまたは新規の修正タスクにする。
3. Codex の実機確認（G5）は、利用上限の回復後にまとめて実施する。
4. 6.1・6.2 は G1・G2 の解決後に再検証し、管理委任の有効化を判断する。

# ローカル除外の決定（2026-11-22）

上の記述（Pi MCP の調査、ギャップ分析の G2・G4 など）は経緯として残す。以下が現在の決定で、上と食い違う場合はこちらを優先する。

## 決定

- 利用者の決定により、ローカル型のエージェント MCP（Pi など、ローカルで動くモデルを使う MCP）を委任先から外す。優先順は「異系統のクラウド型エージェント MCP → 現在のクライアントのネイティブサブエージェント」の 2 段とする。
- 公開された実行形態がローカルの MCP は、要件 1.4 の「クラウド型と確認できないもの」として候補から外す。実行形態は公開された値で判断し、stdio などの接続方式を根拠にしない。Codex MCP（本仕様が配布する管理対象。Codex CLI を起動し、推論はクラウドで行う）はクラウド型の代表例として残す。
- 要件 4 は「対応するエージェント MCP の技術要件」に一般化して残す。旧要件 2.5（ローカル割り当てを有効にしない）は削除した（欠番。番号は詰めない）。
- 上流 subagent-model-policy の `RolePolicy.localModelIds` と `subagents.localModels` は上流に残し、本仕様は使わない。上流仕様は変更しない。将来ローカルを再導入する場合に再検討する。
- Pi・Muse など他のクライアントが指揮役の場合に、そのクライアントを Claude Code や Codex とみなさない一般則は残す。Pi を委任先にしないだけで、Pi を指揮役にする話は削らない（ただし Pi の登録の読み取りは設計から外したため、Pi が指揮役のときは、読み取りとネイティブの起動経路が確認されるまで「候補を選べなかった理由」を返す）。

## 根拠

- 実機（`poc/codex-delegation-live/result.md` の 6.2）で、Ollama 上のモデルは次の理由で実用に足りなかった。ツールに対応しないモデルがある（400）、大きなコーディング向けモデルが編集の呼び出しを構造化せず本文に書く、動くモデルは 13GB 級で重い、`pi_capabilities` の応答の形（`execution`・`access_modes`・`thinking_levels`）が接続部品の契約（`tier`・`models[].accepted`）と合わない（G2）、公開される推論量が `off` だけで `medium` / `high` を要する役割に使えない。
- ローカル段を残したまま G2・G4 を直しても、上の能力不足で実際には選ばれないため、複雑さ（段・設定・表示・試験）に見合わない。

| 論点 | 判断 | 理由 |
|---|---|---|
| 保存済みの `delegation[host].local` | 移行しない。残っていれば適用前に理由を表示して拒否する。CLI の `host:local=` も拒否 | 未リリースで利用者がいない。黙って無視すると、ローカルに委任されると思い込んだまま進む恐れがある |
| 能力の項目名 | `tier` のまま（値は `cloud` だけを候補にする） | 実装済みの Codex MCP が `tier: "cloud"` を公開しており、項目名を変えると公開形式の変更が増える |
| 確認済みアダプターが無い登録 | 不適格とする（既定で Pi のアダプターを当てはめる現在の実装をやめる） | 契約を確認していない MCP を推測で使わない（1.4） |
| 直接起動のガードの対象 | `pi_start` を外し、確認済みアダプターの起動操作（`codex_start`）だけにする | Pi 固有の部分を残さない。なお、cc-sdd 作業中に Pi を直接起動する経路は止まらなくなる（要確認として利用者に提示） |
| Pi が指揮役のとき | 登録を列挙せず、理由を返す | Pi の登録の読み取りを設計から外したため。ネイティブの起動経路も未確認 |

## 残る問題の解決方針

- G1（管理入口の参照がモデルに届かない）: 案 B。上流フックが `delegate.mjs start|status|stop` の決まった形の Bash 呼び出しを書き換えて `--reference` を付け足す。上流フックは Codex にも書き換えの応答（`updatedInput`）を返す実装があるが、Codex が Bash の入力の書き換えを反映するかは要確認（利用上限のため未実測）。確認できるまで Codex を指揮役とする管理委任は有効化しない。
- G3（ネイティブ単独の事前確認が常に拒否される）: 「外部委任の配置あり」を、導入台帳の `delegate.mjs` の有無ではなく、現在のホストの `delegation[host].cloud`（未設定なら `codex.enabled` からの引き継ぎ）から同系統を除いた候補が 1 つ以上あるかで判定する。判定は設定の静的な内容で行う。上流の部品の変更を伴うため、上流仕様の改訂で扱うかは要確認。
- G2・G4 は Pi 固有のため対象外。G5〜G13 は変わらない。

影響の一覧（コード・テスト・タスク・他仕様）は `design.md` の「変更の影響」にまとめた。
