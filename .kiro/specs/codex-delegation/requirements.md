# Requirements Document

## Project Description (Input)
cc-sdd の利用者は、指揮役のクライアントや導入済みの MCP が異なる環境で、製造・レビュー・設計をエージェントに委任する。現状は、このリポジトリや skyshare の個別の指示と Codex 向けの構成に選択が依存する。セットアップで登録済みのエージェント型 MCP を見つけ、候補と優先順を設定する。各委任の直前にモデル ID と機能を確認し、ローカル MCP、異なる系統のクラウド MCP、ネイティブサブエージェントの順に、役割に適合する候補を選ぶ。

## Introduction

cc-sdd の利用者が、現在のクライアントにかかわらず、登録済みのエージェントの中から役割に合う委任先を使えるようにする。設定時に候補と優先順を選び、委任直前に最新の公開情報で利用可否を確認する。

## Boundary Context

- **対象** — セットアップにおける登録済み MCP の探査、候補と順序の設定、実行時の選択と切り替え、ローカル MCP の適格条件。
- **対象外** — ハーネス本体とモデルの導入・認証、MCP の背後にあるモデル提供先の直接確認、cc-sdd 本体の改変、特定プロジェクト専用の試験手順。
- **隣接仕様** — installer-core は導入・更新の入口と設定の保存を提供する。subagent-model-policy は役割・モデル・推論量・権限の条件と、ネイティブ起動の方針を定める。既存の Codex MCP の利用選択と導入対象クライアントの選択は独立して扱う。

## Requirements

### Requirement 1: セットアップでの探査と優先順の設定

**目的** — 利用者が設定画面やファイルを一つずつ探さずに、登録済み MCP の中から委任先を選択できるようにする。

#### Acceptance Criteria

1. When 利用者が cc-sdd-bootstrap の導入または更新を行うとき, the 委任機能 shall その作業の中で委任をセットアップできるようにする。
2. When 利用者が委任をセットアップするとき, the 委任機能 shall 対象クライアントに登録済みの MCP を機械的に列挙する。
3. When 登録先がエージェント型と確認できるとき, the 委任機能 shall サーバーの識別名、ハーネスの系統、ローカル型かクラウド型かを利用者に示す。
4. If MCP が単純応答型か、エージェント型・ハーネスの系統・ローカル／クラウドの区分を確認できないとき, then the 委任機能 shall その MCP を委任候補から外す。
5. When 利用者が委任候補を選ぶとき, the 委任機能 shall ローカル段とクラウド段のそれぞれで先に試す順を指定し、保存できるようにする。
6. If 利用者が登録済みの MCP をセットアップで選択していないとき, then the 委任機能 shall その MCP に委任しない。
7. When 利用者が委任設定の変更を指定せずに更新するとき, the 委任機能 shall 既存の利用選択と候補順を引き継ぐ。

### Requirement 2: 委任直前の確認とモデルの見直し

**目的** — 利用者が候補のモデルが変わるたびに設定を書き直さず、明示的な固定指定も維持できるようにする。

#### Acceptance Criteria

1. When cc-sdd がサブエージェントへの委任を必要とするとき, the 委任機能 shall 選択対象となる承認済み MCP の受付モデル ID と関連する実行機能を起動前に機械的に確認する。
2. The 委任機能 shall MCP が公開する受付モデル ID をモデル候補の根拠とする。
3. When 自動選択中のモデル候補が変わったとき, the 委任機能 shall 最新の公開一覧から役割条件に適合するモデルをその委任で選ぶ。
4. If 利用者が明示固定した MCP のモデル ID が公開一覧にないか、役割条件を満たさないとき, then the 委任機能 shall 固定値を保持し、その候補を外して次の候補を確認する。
5. If 役割条件を満たすローカル公開モデルがないとき, then the 委任機能 shall その役割のローカル割り当てを有効にしない。

### Requirement 3: 実行先の固定優先順

**目的** — 指揮役のクライアントを変更しても、利用可能な候補を同じ原則で使えるようにする。

#### Acceptance Criteria

1. The 委任機能 shall ローカル型エージェント MCP、クラウド型エージェント MCP、現在のクライアントのネイティブサブエージェントの順で、役割条件に適合する候補を選ぶ。
2. When 同じ段に複数の適格候補があるとき, the 委任機能 shall セットアップで利用者が保存した順に候補を選ぶ。
3. If クラウド型 MCP のハーネスが指揮役を実行しているクライアントと同じ系統のとき, then the 委任機能 shall その MCP を候補から外す。
4. When Codex MCP がクラウド段の承認済み候補で、指揮役のクライアントが Codex 系統以外であるとき, the 委任機能 shall 他のクラウド型 MCP と同じ適格条件と設定順を適用する。
5. If 適格な MCP 候補がなくネイティブでの起動もできないとき, then the 委任機能 shall 起動を行わず、利用者に委任先を選べなかった理由を示す。

### Requirement 4: ローカル MCP の技術要件

**目的** — ローカルで委任した処理を実行・追跡でき、役割に必要な権限と推論量を守れるようにする。

#### Acceptance Criteria

1. The 対応ローカル MCP shall エージェント型であること、ハーネスの系統、ローカル実行であること、受付モデル ID、対応する権限と推論量を機械可読に公開する。
2. When 対応するモデル・権限・推論量で作業先を指定した依頼を受け付けたとき, the 対応ローカル MCP shall 作業を開始し、状態確認と停止に使えるジョブ識別子を返す。
3. When 読み取り専用の依頼を実行するとき, the 対応ローカル MCP shall 編集・書き込み・シェルのツールを提供せず、作業先への書き込みを実行環境でも禁止する。
4. When 製造のために書き込み許可を指定した依頼を実行するとき, the 対応ローカル MCP shall 指定された作業先での編集とテスト実行を許可する。
5. If 要求されたモデル・権限・推論量の組み合わせに対応しないとき, then the 対応ローカル MCP shall 別のモデルや権限、推論量で起動せず、理由を返す。
6. When 利用者がジョブ識別子を使って状態の取得または停止を求めたとき, the 対応ローカル MCP shall 対象のジョブの状態または停止結果を返す。

### Requirement 5: 起動前後の失敗と切り替え

**目的** — 一時的に使えない委任先から回復し、同じ作業への二重実行を防げるようにする。

#### Acceptance Criteria

1. If 選んだ MCP が起動前に利用できないと確認したとき, then the 委任機能 shall 失敗した候補を外し、設定済みの順で次の適格候補を確認する。
2. If 起動要求の後で作業が開始済みか、または継続中か判断できないとき, then the 委任機能 shall 切り替えの前に先行ジョブの状態を確認する。
3. While 先行ジョブの停止または終了が確認できず、同じ書き込み作業を引き継ぐとき, the 委任機能 shall 別の委任先を起動せず、確認できない状態を利用者に示す。
