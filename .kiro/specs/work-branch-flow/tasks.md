# Implementation Plan

> 順序の方針: feasibility-review の方針にならい、最初のタスク群（1）で、配置した入口を実機（Claude Code・Codex）で動かして前提を確かめる。確かめられなければ以降に進まず設計へ戻す。`lib/catalog.mjs`・`package.json`・カタログの試験は feasibility-review の実装タスクと同じファイルを触るため、2 つの spec のカタログのタスクは同時に進めない。

- [ ] 1. 作業前のブランチ確保を端から端まで動かす（最小の形と実機の確認）
- [ ] 1.1 設定の項目 3 つを足す
  - 作業前のブランチ確保・検証後の PR 作成を、それぞれ有効・無効にする真偽の項目（既定は有効）と、基底ブランチの一覧の項目（既定は `main,master,develop`。カンマ区切りで 1 件以上、各要素は空でなく、空白・制御文字・先頭の `-` を含まない）を、設定の項目定義に足す
  - 導入・更新が、欠けた項目を既定値で補う既存の仕組みに乗る（導入コマンドの処理は変えない）
  - 単体試験で、既定値、不正な値（空・空白入り・先頭が `-`）の拒否、欠けた項目の補いが確かめられる
  - _Boundary: Config fields_
  - _Requirements: 1.1, 1.2, 1.3, 1.7_
- [ ] 1.2 基底ブランチでの作業を拒否する最小の入力・操作のフックを作り、配置物として登録する
  - 判定: 対象の入力の分類（5 つのコマンド）、基底ブランチ（ブランチなしを含む）の判定、操作の粗い分類（読み取り・ブランチの作成や切り替え・作業）、最大回数つきの拒否の判断、案内と拒否の理由の基本の文言を作る。判定は入力から結果だけを計算する
  - 入口: 標準入力の JSON・設定・入力の作業場所のブランチを使い、対象の入力で作業の状態を作って案内を追加の文脈で返し、操作の前で拒否の出力を返す。状態は OS の一時ディレクトリの下に置く。設定が無効・読めない・ブランチを判定できない・内部の失敗では出力せず終了コード 0 で通す
  - カタログに 2 つのスクリプトと、両ツールの入力・操作の前のフックを登録し、配る範囲にも足す
  - 単体試験と標準入力の試験（一時の git リポジトリ）で、基底で作業が拒否され、作業ブランチでは何も出ず、状態がリポジトリの中に作られないことが確かめられる
  - _Depends: 1.1_
  - _Requirements: 1.4, 1.6, 2.1, 2.2, 2.3, 2.6, 3.1, 3.2, 3.3, 3.6, 3.9, 3.10, 3.11, 3.12, 7.5_
- [ ] 1.3 実機で配置した入口の拒否→案内→切り替え→作業を確かめる
  - 前提: 認証済みの `claude`・`codex`、一時の Codex の設定でのフックの信頼の承認（検証専用の承認の省略を使う）
  - 一時のリポジトリに配置物とフックの登録を置き、基底ブランチで対象の入力を送って、Claude Code・Codex それぞれで、案内が届き、作業が拒否され、作業ブランチへ切り替えてから作業できることを確かめる。`poc/work-branch-flow/run.mjs` に場面を足し、結果を `result.md` に追記する
  - Codex でブランチを作れない場合（`.git` が読み取り専用）に、作れない理由を伝えて止まることも確かめる。確かめられない項目は未確認として結果に残す
  - 前提が崩れたら以降に進まず、設計へ戻す
  - _Depends: 1.2_
  - _Requirements: 3.1, 3.12, 7.1_

- [ ] 2. 作業前のブランチ確保を仕上げる
- [ ] 2.1 実際の作業場所のブランチで判定する
  - 操作の入力から作業場所を求める判定を作る（Claude Code は対象ファイルの絶対パスと先頭の絶対パスへの `cd`、Codex は `apply_patch` の対象パスと作業ディレクトリ）。パスの無い操作・相対の `cd` は求められないものとする
  - 操作が「作業」と分類されて場所を求められたときだけ、直近の作業場所を状態に記録する（読み取りの操作では更新しない）。ブランチの判定は、求めた場所、記録した場所、入力の作業場所の順に選び、存在しない場所・git の外は次の候補へ進む
  - 単体試験と標準入力の試験で、本体が基底・worktree が作業ブランチの構成で worktree への書き込みが許可されること、本体の checkout の読み取りを挟んでも記録が変わらないことが確かめられる
  - _Depends: 1.2_
  - _Requirements: 3.13_
- [ ] 2.2 拒否の回数・解除・切り替え後の扱いを仕上げる
  - 拒否を入力ごとに最大 2 回にし、通常の入力で回数だけ 0 に戻す。別の `/kiro-*` のコマンドの入力で対象を解除し、次の対象の入力では記録を引き継がない。基底でないと判定できたら解除する
  - ブランチの作成・切り替えを試みた後は拒否しない（別の仕組みがその操作を拒否して案内した場合を含む）。拒否のたびに追加の文脈の案内は重ねず、拒否の理由だけを返す。別の仕組みの拒否を取り消さない出力にする
  - 単体試験と標準入力の試験で、対話を挟んだ後の書き込みの拒否、入力ごとの回数の巻き戻し、別のコマンドでの解除、切り替えの試行の後は拒否しないこと、通常の入力で案内が繰り返されないことが確かめられる
  - _Depends: 2.1_
  - _Requirements: 1.4, 2.4, 2.5, 3.5, 3.7, 7.3_
- [ ] 2.3 拒否と案内の文言を仕上げる
  - `kiro-impl` の入力では、その spec を格納した作業用ブランチがリモートにある場合はそこへ切り替えること、ローカルに spec が無い可能性があることを足す。ブランチを作れないときは理由を利用者に伝えて止まるよう書く
  - 文言に、特定の別の仕組みの名前を含めない
  - 単体試験で、各文言の内容と、特定の仕組みの名前が無いことが確かめられる
  - _Depends: 2.2_
  - _Requirements: 3.4, 3.8, 6.5_

- [ ] 3. 検証後の PR 作成を足す
- [ ] 3.1 PR の案内と終了の停止の判断を作る
  - `kiro-validate-impl` の入力の分類、検証後の案内（GO で作業ブランチの上なら push と PR を通常の操作で試みること、設定の既定の運用であり事前の指示として扱うこと、NO-GO なら作らず報告すること、別の仕組みが拒否して案内したら従うこと。タイトル・本文は固定しない）、終了の停止の判断（PR が無いと判定できたときだけ 1 回止める）と停止の文言を作る
  - 単体試験で、PR が無いときだけ止まること、2 回目の終了・停止済み・同じセッションに検証の入力が無い・PR あり・判定できないでは止まらないこと、案内に既定の運用であることが入ることが確かめられる
  - _Depends: 2.3_
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 5.1, 5.2, 5.3, 5.4, 5.5_
- [ ] 3.2 検証後の入力と終了のフックの入口を作る
  - 検証の入力で、設定が有効なら現在のブランチによらず状態を作って案内を返す。終了のフックで、直近の作業場所のブランチと `gh` による PR の有無（時間の上限あり。未導入・未認証・GitHub 以外・失敗は判定できないとして通す）を使って判断し、止めたら止めた印を状態に残す。終了のフックを両ツールに登録する
  - 設定が無効のときは案内も停止もしない。停止の記録をリポジトリの中に残さない
  - 偽の `gh` を使う標準入力の試験で、PR 無しなら 1 回止まって 2 回目は通ること、`gh` が無い・失敗で通ること、設定が無効で何も出ないこと、リポジトリの中に何も作られないことが確かめられる
  - _Depends: 3.1_
  - _Requirements: 1.5, 4.1, 4.4, 5.1, 5.2, 5.3, 5.6_

- [ ] 4. 運用の区画の文章とカタログを仕上げる
- [ ] 4.1 運用の区画と登録の一致を確かめる
  - 運用の区画に、新機能追加系の作業の前に作業用ブランチへ移ること、`/kiro-validate-impl` の GO の後に作業ブランチの PR を作ること、2 つのフローが設定で無効にでき既定は有効であること、別の仕組みの拒否と案内に従うことを、Claude Code 用・Codex 用に同じ内容で書く。特定の仕組みの名前を含めない。フックの信頼が未承認でも文章で促されるようにする
  - カタログ・`package.json`・配る範囲の一致を確かめる試験を足す
  - 試験で、両ツールの文章が同じ項目を含み、特定の仕組みの名前を含まず、フックの登録と配るファイルの一覧が一致することが確かめられ、試験一式が通る
  - _Depends: 3.2_
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 7.1, 7.4_

- [ ] 5. 実機で全体を確かめる
- [ ] 5.1 別の仕組みを重ねた構成と PR の停止を実機で確かめる
  - 前提: 1.3 と同じ。別の仕組み（ブランチと PR の作成を別の手順に集約する仕組み）を重ねた構成は Claude Code で確かめる（Codex は登録に信頼の承認が要るため、確かめられなければ未確認として残す）
  - 別の仕組みがブランチの作成を拒否して別の手順を案内しても行き詰まらず、案内に従って作業ブランチで作業できること、同じセッションで worktree へ移った後の検証で PR が無ければ 1 回止まって 2 回目は通ること、手順書の先読みの拒否と重なっても案内が最終的に届くことを確かめ、結果を `result.md` に追記する
  - _Depends: 4.1_
  - _Requirements: 3.5, 3.7, 3.13, 5.1, 5.2, 7.2_
