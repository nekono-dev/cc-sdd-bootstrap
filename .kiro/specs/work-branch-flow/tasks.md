## Implementation Notes
- 1.2: 操作の分類は設計の粗い分類から次のとおり細かくした。一覧表示だけの `git branch`・`git worktree list` は `read`（切り替えの試行にしない）、名前を取る `git branch`・`git worktree add|remove|prune|move`・`git switch`・`git checkout <ブランチ>` は `branch`、`git checkout -- <file>`・`git checkout .` は `work`。`rg --pre`・`git diff|log|show --output|--ext-diff|--textconv`・`sort -o`・`find -delete|-exec` などの書き込み・実行を伴うオプションは `work`（迷う形は `work` に倒す）。`git checkout <ファイル>`（`--` なし）はブランチと区別できず `branch` に分類する（残る限界）。
- 1.2: 設定ファイルが無いときは既定値（有効）で動く。`workflow` がオブジェクトでないときは通す（要件 1.6）。
- 1.2: 承認の記録（Codex）の件数が、フックの登録の追加に伴い 8 → 10 になった（`test/cli.test.mjs`・`test/cli.e2e.test.mjs`）。以後の登録（Stop など）で再び増える。
- レビュー役（Codex・読み取り専用）の環境では `/tmp` に書けず、入口の試験を実行できない。入口の試験の確認は親が行う。
- 1.2（実機の確認 1.3 で判明）: Claude Code のモデルは、切り替えを `&&`・`||`・`( )` でつないだ複合コマンドで実行する。連結を含むものをすべて「作業」とすると、切り替えが 2 回拒否されてモデルが諦める。このため操作の分類は、引用符の外の区切りで部分に分け、各部分を分類して合わせる形にした（どれかが作業・分類できない構造なら作業、作業が無く切り替えがあれば切り替え、全部読み取りなら読み取り）。引用符は外した値で判定し、行継続は取り除いてから判定する。区切りの前後が空なら作業。拒否と案内の文言に「ブランチの作成・切り替えは単独のコマンドで」の 1 文を足した。
- 1.3: Codex（`workspace-write`）では `.git` が読み取り専用でブランチを作れず、作れない理由を利用者へ伝えて止まる（要件 3.8 のとおり）。拒否 → 切り替え → 作業の全体は Claude Code でのみ確認した。追加の文脈（入力時の案内）が届いたかは、ストリームに出ないため未確認。ブランチ名を指定しない入力では、モデルは拒否の理由の「分からなければ利用者に尋ねる」に従って確認して止まる（`-p` では終わる）。
- 2.1: 作業場所を求める `cd` は保守的に、引用符の外の展開・コメント・置換の記号（語の先頭の `#`・`~`、位置を問わない `!`・`\`・`*`・`?`・`[`・`{`・`$`・バッククォート）や確定できない形（`cd -`・複数引数・オプション）は求めない（null）。その場合は直近の作業場所（②）か入力の作業場所（③）で判定する。`location` は、作業の操作で場所を求められたときだけ記録する（存在しない場所も記録するが、判定の候補としては飛ばす）。
- 2.2: `classifyPrompt` の区分は、対象の 5 つ（`target`）、`kiro-validate-impl`（`validate-impl`）、それ以外の kiro コマンド（`other-kiro`）、通常の入力（null）。`turn` は `other-kiro`・`validate-impl` の入力で消え、通常の入力では残して拒否の回数だけ 0 に戻る（`switchTried` は戻さない）。PreToolUse で基底でないと判定できるのは、作業場所を求める「作業」の操作のときだけなので、読み取りの操作では `turn` を消さない。
- 2.3: 文言の内容（現在のブランチ名・切り替え・新規作成・利用者に尋ねること・作れないときは理由を伝えて止まること・`kiro-impl` のリモートの作業用ブランチとローカルに spec が無い可能性・単独のコマンドの 1 文）と、特定の仕組みの名前が無いことは、1.2 の実装と試験で満たしていた。2.3 では実装を足さず、受け入れ条件を既存の試験（`test/work-branch-gate-rules.test.mjs` の文言の試験 4 件）と突き合わせて確認した。実機（1.3）では、ブランチ名を指定しない入力で、モデルが「分からなければ利用者に尋ねる」に従い確認して止まった（要件 3.3 のとおり。変更しない）。
- 3.1: `decideStop` は、型が想定外（`stopHookActive` が真偽値でない、`validated.stopped` が偽でない、`prExists` が偽でない、`branch` が文字列でない、`bases` が配列でない）のときは必ず通す。止めるのは全部が明示的に満たされたときだけ。`messagePrContext` は GO・NO-GO・MANUAL_VERIFY_REQUIRED の 3 つの結果（`kiro-validate-impl` の定義）を扱う。
- 3.2: 2 つのフローの設定は独立。作業前のブランチ確保（対象の入力・通常の入力・他の kiro コマンド・PreToolUse）は `workflow.branchGate`、検証後の PR（`kiro-validate-impl` の入力・Stop）は `workflow.prAfterValidate` だけに従う。Stop は入口で `prAfterValidate` を再確認する（検証入力の後に無効にされても止めない）。停止は、状態の保存に成功してから出力する。Codex の承認の記録の件数は 10 → 11（Stop は両ツールに足すが、Codex の設定に書かれるのは Codex 分の 1 件）。
- 4.1: 運用の区画の文章は、拒否と停止を断定せず実挙動の条件で書く（拒否は入力ごとに最大 2 回で、作成・切り替えを試みた後と判定できないときは拒否しない。停止は PR が無いと判定できたときだけ）。区画の CLAUDE.md・AGENTS.md への書き込みは導入側の `install-rules.mjs` の `replaceSection` が行う。このリポジトリ自身の CLAUDE.md・AGENTS.md への反映は、導入コマンドの更新（自己適用）で行う（この spec の範囲外）。
- 5.1: 実機で、別の仕組みを重ねた構成（Claude Code）が行き詰まらず worktree で作業でき、終了の停止が両ツールで働くことを確かめた（`poc/work-branch-flow/result.md` の場面 G・H）。未確認として残す: 同じセッションで worktree へ移った後の検証での Stop（統合試験で確認）、実際の PR の作成、Codex に別の仕組みを重ねた構成。
