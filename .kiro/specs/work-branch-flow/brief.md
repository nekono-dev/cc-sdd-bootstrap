# Brief: work-branch-flow

## Problem
cc-sdd の作業（`/kiro-discovery` から `/kiro-impl` まで）は、`develop` や `main` などの基底ブランチの上でそのまま始められる。そのため、作業用ブランチを切らないまま spec や実装が基底ブランチに積まれ、終わった後の PR も作られないことがある。導入先のリポジトリごとに、この運用を文章で頼むしかなく、読み落としを止められない。

## Current State
- cc-sdd 自身は、作業ブランチの作成も PR の作成も求めない。
- 本リポジトリの kiro-gate は、`/kiro-*` で始めた依頼で手順書を読むまで他のツールを拒否する。コマンドの検出と最小の状態を持っている。
- 設定ファイル（`.cc-sdd-bootstrap.json`）と運用の区画の文章は installer-core が持ち、下流の spec が項目と文章を足せる。
- 別リポジトリの branch-release-workflow（以下 brw）は、`git checkout -b`・`git switch` の作成・再開と `gh pr create` を PreToolUse のフックで拒否し、`brw create`・`brw resume`・`brw publish` を案内する。brw はリモートのブランチから worktree を作り直す `brw resume` を持つ（2026-11-25 に確認）。
- cc-sdd-bootstrap は brw を知らない前提のため、現在は連携が無い。

## Desired Outcome
- 設定ファイルのオプションで有効・無効を決められる運用フローが、既定で有効になっている。フローは 2 つ。
  1. **作業前のブランチ作成**: 新機能の追加にあたる作業（下の対象）を始める前に、作業用ブランチにいる。基底ブランチの上にいる間は、他のツールを拒否してブランチの作成・切り替えへ誘導する。
  2. **`/kiro-validate-impl` の後の PR 作成**: 検証が GO のときは作業ブランチの PR を作る。PR を作らないまま応答を終えようとしたら、一度だけ止める。
- brw 導入済みのブランチでは、brw のフックがブランチ作成・切り替え・`gh pr create` を拒否し、エージェントを brw の手順へ移す。cc-sdd-bootstrap は brw の有無を判定せず、同じ操作（`git switch -c`、`gh pr create`）を試みるだけで済む。brw が無ければ、その操作がそのまま通る。
- 判定できないとき（git でない場所・基底ブランチを決められない場合など）の扱いは、要件で「止める」か「通す」かを決めて明記する。

## Approach
決定済み（2026-11-25、利用者の選択）:
- ① 作業前のブランチ作成は**フックで止める**。入力時のフックで対象コマンドを検出し、ツール起動前のフックで「現在のブランチが基底ブランチ・detached HEAD」の間は他のツールを拒否する（kiro-gate と同じ時点・同じ検出を共有する）。拒否の理由に、案内を固定の文章で入れる。
- 基底ブランチの判定は、既定の一覧（`main`・`master`・`develop`、origin の既定ブランチ）＋設定ファイルでの変更。brw の宣言ファイルは読まない。
- `/kiro-impl` を作業ブランチ以外で始めた場合の案内は、固定の文章（案 A）: 「spec を格納した既存の作業ブランチがリモートにあればそこへ切り替え、無ければ新規作成。どれか分からなければ利用者に尋ねる」。リモートのブランチの探索はフックでは行わない。切り替えと再開は git か brw（`brw resume`）が行う。
- ② PR の作成は**文章で促し、終了時に止める**。運用の区画と `/kiro-validate-impl` の入力時の文脈で「GO の後は PR を作る」と伝え、応答を終えるときの Stop フックで、PR が無ければ一度だけ止める。

## Scope
- **In**:
  - 設定ファイルの項目（2 つのフローそれぞれの有効・無効。既定は両方とも有効。基底ブランチの一覧）と、installer-core の項目定義への登録。
  - ① 作業前のブランチ作成の関門（対象コマンドの検出・基底ブランチの判定・拒否と案内）。対象は `kiro-discovery`、`kiro-spec-init`・`kiro-spec-quick`・`kiro-spec-batch`、`kiro-impl`。
  - ② `/kiro-validate-impl` の後の PR の案内（運用の区画の文章・入力時の文脈）と、終了時の停止。
  - 運用の区画の文章（Claude Code と Codex の両方）。
  - フックの登録（Claude Code・Codex の両方）。
  - 前提を確かめる PoC。
- **Out**:
  - brw の呼び出し・検出・宣言ファイルの読み取り（brw を一切知らない）。
  - ブランチ名の決め方・命名規則の検証（brw や利用者の運用に任せる）。
  - リモートのブランチの探索・候補の提示。
  - PR のタイトル・本文の自動生成の仕組み（エージェントが作る）。
  - `/kiro-validate-impl` の GO・NO-GO の機械的な判定。
  - 既存 spec（kiro-gate など）の設計のやり直し。

## Boundary Candidates
- 設定の項目と既定値（installer-core の項目定義への登録）。
- ① 作業前のブランチの関門（入力時の検出・ツール起動前の拒否）。
- ② 検証後の PR の案内と終了時の停止。
- 運用の区画の文章。

## Out of Boundary
- 手順書の先読みの強制（kiro-gate）。
- cc-sdd の導入（session-install）。
- 子のエージェントのモデルの決まり（subagent-delegation）。
- ブランチ・PR の運用の実体（brw が持つ。cc-sdd-bootstrap は知らない）。
- 設計・タスクの実現性の確認（feasibility-review）。

## Upstream / Downstream
- **Upstream**:
  - installer-core（設定の項目定義・カタログへのフックと運用の区画の登録）。
  - kiro-gate（`/kiro-*`・`$kiro-*` の検出、入力時とツール起動前のフックの形。検出の規則は共有し、重複して作らない）。
- **Downstream**: このリポジトリと導入先の運用。brw が PR 作成のラッパーを実装した後の組み合わせ（brw 側の実装は本 spec の範囲外）。

## Existing Spec Touchpoints
- **Extends**: なし。新しい境界とする。
- **Adjacent**:
  - kiro-gate（同じ入力時・ツール起動前に動く。コマンドの検出の規則を共有する。先読みの拒否と本 spec の拒否が併存したとき、どちらの理由も届くようにする）。
  - installer-core（設定の項目定義・カタログ）。
  - feasibility-review（同じ入力時の検出を共有する見込み。未着手）。

## Constraints
- cc-sdd のスキルを改変・複製しない。外から指示する（追加の文脈・運用の区画・フック）。
- brw を知らない。brw の有無で分岐するコードを持たない。brw のフックによる拒否は、エージェントが拒否の理由を読んで brw の手順へ進むことで成立する。
- 厳密さのためにコードを増やさない。判定できないときの扱い（止めるか通すか）を要件で決めて明記する。
- 両ツール（Claude Code・Codex）に同じ規則を適用する。
- PR の作成は、エージェントの既定の決まり（利用者が求めたときだけ作る）と食い違う。設定の既定を「有効」にしたことが、利用者の事前の指示にあたることを、運用の区画の文章に明記する。
- 設計前に PoC で確かめる前提:
  - (a) ツール起動前の拒否が、基底ブランチの間に他のツールを止める一方、ブランチの作成・切り替え（`git switch`・`git checkout`）と読み取りを通せるか。brw のフックが同じコマンドを拒否・案内したとき、2 つの拒否が両ツールで衝突しないか。
  - (b) brw が新しい worktree（別のディレクトリ）を作った後、セッションの作業場所は元のままでもエージェントはそこで作業する。このとき「現在のブランチ」をどこで判定するか（セッションの作業場所か、操作するファイルの場所か）。判定を誤ると、worktree で作業していても拒否が続く。
  - (c) Stop フック（応答を終えるときのフック）が、Claude Code と Codex の両方で「一度だけ止めて続きをさせる」ことができるか。無限に止め続けない仕組み（再入の印）が要る。
  - (d) `/kiro-validate-impl` を実行したことの記録（kiro-gate の最小の状態を拡張するか）と、PR の有無の判定（`gh pr view` など）が、gh が無い・未認証の環境で安全に働く（止めずに通す）か。
  - (e) Codex のフックが worktree の中でも本体の checkout の `.codex/hooks.json` を読む前提（`poc/codex-worktree-hooks/`）が、本 spec の新しいフックにも当てはまるか。
- このリポジトリで新しいフックを足す spec は、develop に取り込むまでの一時的な状態として、自己適用の後の確認（普通の checkout の写しと取り込み後の worktree）をタスクに置く（roadmap の既定）。
