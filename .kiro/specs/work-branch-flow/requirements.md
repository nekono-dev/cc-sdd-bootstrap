# 要件文書

## Project Description (Input)

**対象となる利用者**：cc-sdd-bootstrap を導入したリポジトリの開発者と、そこで指揮役として作業する Claude Code および Codex。

**解決する問題**：cc-sdd の作業（`/kiro-discovery` から `/kiro-impl` まで）は、`develop` や `main` などの基底ブランチの上でそのまま始められる。そのため、作業用ブランチを切らないまま spec や実装が基底ブランチに積まれ、検証が済んだ後の PR も作られないことがある。この運用を文章で頼んでも、読み落としを止められない。

**実現すること**：設定ファイルのオプション（既定は有効）で、次の 2 つの運用フローを足す。

- 新機能追加系の作業の前に、作業用ブランチにいることをフックで求める。
- `/kiro-validate-impl` の後は、作業ブランチの PR を作る（文章で促し、作らないまま終えようとしたら止める）。

branch-release-workflow（以下 brw。ブランチと PR の作成を独自の手順に集約する別の仕組み）は知らない前提とする。ブランチ作成と PR 作成の通常の操作を試みるだけにし、brw が導入されていればその仕組みの拒否によって brw の手順へ移る。

**対象外**：brw の検出・呼び出し・宣言ファイルの読み取り、ブランチ名の決め方、リモートのブランチの探索、PR のタイトル・本文の生成、`/kiro-validate-impl` の GO・NO-GO の機械的な判定。

詳細な背景は同じディレクトリの brief.md を、実機で確かめた前提は実機検証で確認済み（記録は削除済み）。

## Introduction

work-branch-flow は、cc-sdd の作業を作業用ブランチの上で進め、検証の後に PR まで届けるための運用フローである。2 つのフロー（作業前のブランチ確保、検証後の PR 作成）を、設定ファイルのオプションで個別に有効・無効にできる。どちらも既定は有効である。

作業前のブランチ確保は、フック（作業環境の動作の節目で自動実行される処理）で、基底ブランチ（日々の作業を直接積まない統合用のブランチ）の上にいる間の最初の作業を 1 回だけ拒否し、作業用ブランチへ移るよう案内する。検証後の PR 作成は、文章と入力時の案内で促し、PR を作らないまま応答を終えようとしたときに 1 回だけ止める。

## 対象と境界

- **対象**：設定のオプション、新機能追加系の作業を始める入力の検出、基底ブランチの上での最初の作業の 1 回だけの拒否と案内、`/kiro-validate-impl` の後の PR 作成の案内と終了時の 1 回だけの停止、運用の区画の文章、Claude Code と Codex の両方への適用。
- **対象外**：brw の検出・呼び出し・宣言ファイルの読み取り、ブランチ名の命名規則の検証、リモートのブランチの探索と候補の提示、PR のタイトル・本文の生成、GO・NO-GO の機械的な判定、基底ブランチでの commit・push の拒否、cc-sdd 本体の改変。
- **brw などの別の仕組みとの関係**：work-branch-flow は、ブランチ作成と PR 作成のための通常の操作（`git` による作成・切り替え、`gh` による PR 作成）を案内するだけで、特定の仕組みの有無で振る舞いを変えない。別の仕組みがその操作を拒否して別の手順を案内したときは、エージェントがその案内に従う。work-branch-flow が操作を通すことは、別の仕組みの拒否を解除することを意味しない。
- **kiro-gate との関係**：`/kiro-*` で始まる入力の検出の規則は kiro-gate と同じものを使う。手順書を読むまでの拒否は kiro-gate が扱う。同じ操作への複数の拒否は理由が 1 つしか届かない（実機検証で確認済み。記録は削除済み）ため、work-branch-flow は入力時の案内と、最大 2 回の拒否で、自分の案内を届ける。
- **installer-core・session-install との関係**：設定ファイルの項目の定義とフックの登録、運用の区画の文章の配置は installer-core が、導入のたびの書き足しは session-install が扱う。この仕様は、項目の意味と、運用フローの内容を定める。
- **強制の前提**：機械的な強制の対象は、フックが有効で、対象の入力とツール操作を判定できる環境とする。Codex のフックの信頼が承認されていない環境では、運用の区画の文章（AGENTS.md）で促すが、機械的な強制は保証しない。
- **既知の制約**：Codex の書き込み制限が厳しい実行（承認なし）では、`.git` に書けず作業ブランチを作れないことがある（実機検証で確認済み。記録は削除済み）。その場合の振る舞いは要件 3 の 8 で定める。

以下では、利用者の入力から次の入力までの作業の区切りを「ターン」、作業環境で継続する一連の会話を「セッション」と呼ぶ。「基底ブランチ」は、設定で決めた基底ブランチの一覧に含まれるブランチ、または origin の既定ブランチを指す。「作業の開始」は、読み取りと作業ブランチへ移るための操作を除く、ファイルの変更をともなう（またはともないうる）ツール操作を指す。受け入れ基準の主語はすべて work-branch-flow とする。

## Requirements

### Requirement 1: 設定のオプション

**目的**：開発者として、2 つの運用フローを設定ファイルで個別に切り替えたい。これにより、運用に合わないリポジトリでは外し、何も設定しなければ既定で有効な運用を得られる。

#### 受け入れ基準

1. The work-branch-flow shall 作業前のブランチ確保と、検証後の PR 作成のそれぞれを、設定ファイルの項目で有効・無効にできるようにする。
2. The work-branch-flow shall どちらの項目も、設定ファイルに書かれていない場合は有効として扱う。
3. The work-branch-flow shall 基底ブランチの一覧を設定ファイルの項目で変更できるようにし、書かれていない場合の既定を `main`・`master`・`develop` とする。
4. While 作業前のブランチ確保が無効である, the work-branch-flow shall 基底ブランチの上での作業を拒否しない。
5. While 検証後の PR 作成が無効である, the work-branch-flow shall PR の作成の案内と終了時の停止を行わない。
6. If 設定ファイルが読めない、または項目の値が不正である, then the work-branch-flow shall 作業を拒否・停止せずに通す。
7. When 導入コマンドが設定ファイルを新しく作る、または欠けた項目を補う, the work-branch-flow shall 2 つのフローの項目を有効の値で書く。

### Requirement 2: 新機能追加系の作業を始める入力の検出

**目的**：開発者として、新しい作業の入口にあたるコマンドだけを作業前のブランチ確保の対象にしたい。これにより、確認や再開などの作業を妨げずに、新規の作業だけを作業ブランチへ導ける。

#### 受け入れ基準

1. When Claude Code または Codex が利用者の入力を受け取り、先頭の空白を除いた入力が `kiro-discovery`・`kiro-spec-init`・`kiro-spec-quick`・`kiro-spec-batch`・`kiro-impl` のいずれかのコマンド（`/` で始まる形と、Codex でスキルを明示して呼ぶ `$` で始まる形を含む）で始まる, the work-branch-flow shall その入力を作業前のブランチ確保の対象にする。
2. The work-branch-flow shall コマンド名の直後が空白または入力の末尾である場合に限り、先頭のコマンドを対象として扱う。
3. When 対象のコマンドの名前が入力の先頭以外に現れる, the work-branch-flow shall その記述を理由として作業前のブランチ確保を始めない。
4. The work-branch-flow shall 作業前のブランチ確保の対象を、利用者が別の `/kiro-*`・`$kiro-*` のコマンドを送るか、現在のブランチが基底ブランチでなくなるまで保つ（コマンドを含まない通常の入力では解除しない。`kiro-discovery` のように利用者との対話を挟んでから書き込む手順でも、書き込みの前に効かせるため）。
5. When 利用者が次の対象の入力を送る, the work-branch-flow shall 以前の入力による拒否済みの記録を引き継がず、最新の入力について改めて判定する。
6. The work-branch-flow shall `kiro-spec-requirements`・`kiro-spec-design`・`kiro-spec-tasks`・`kiro-validate-*`・`kiro-spec-status`・`kiro-steering` など、上に挙げた以外のコマンドを作業前のブランチ確保の対象にしない。

### Requirement 3: 基底ブランチの上での最初の作業の拒否と案内

**目的**：開発者として、基底ブランチの上で新しい作業を始めようとしたときに、作業用ブランチへ移るよう導かれたい。これにより、作業が基底ブランチに積まれることを避けられる。

#### 受け入れ基準

1. While 作業前のブランチ確保が有効であり、対象の入力を受けた後（2.4 の解除まで）で、現在のブランチが基底ブランチである, when エージェントが最初の作業の開始を試みる, the work-branch-flow shall その操作を拒否する。
2. While 現在のブランチがどのブランチにも属さない状態（ブランチなしの状態）である, the work-branch-flow shall その状態を基底ブランチと同じに扱う。
3. When work-branch-flow が操作を拒否する, the work-branch-flow shall 拒否の理由として、現在のブランチ名、作業用ブランチへ切り替えてから続けること、既存の作業用ブランチがあればそこへ切り替え無ければ新しく作ること、どれか分からなければ利用者に尋ねることを、エージェントが読める形で伝える。
4. When 入力が `kiro-impl` で始まる, the work-branch-flow shall 拒否の理由に、その spec を格納した作業用ブランチがリモートにある場合はそのブランチへ切り替えること、ローカルに spec が無い可能性があることを含める。
5. The work-branch-flow shall 拒否を、利用者の入力 1 回につき最大 2 回まで行い、それ以降のその入力の間の操作を拒否しない。次の入力では回数を 0 に戻す（対話の間に誤って作業と分類された操作が回数を使い切って、後の書き込みが素通りすることを避けるため。別の仕組みの拒否と重なって理由が届かない場合に、もう 1 回で届くようにするため。2026-11-25 の PoC で、同じ操作への複数の拒否は理由が 1 つしか届かないことを確認した）。
6. The work-branch-flow shall 読み取りの操作と、作業ブランチへ移るためのブランチの作成・切り替えの操作を拒否しない。
7. If エージェントがブランチの作成・切り替えを試み、別の仕組みがそれを拒否して別の手順を案内する, then the work-branch-flow shall その後の操作をさらに拒否せず、エージェントが案内に従って進められるようにする。
8. If エージェントが実行環境の制約でブランチを作れない, then the work-branch-flow shall 作れない理由を利用者に伝えて作業を止めるよう、拒否の理由に含める。
9. If 現在のブランチを判定できない（git のリポジトリの外、判定に必要な情報が得られない、など）, then the work-branch-flow shall 作業を拒否せずに通す。
10. While 現在のブランチが基底ブランチではない, the work-branch-flow shall 対象の入力であっても作業を拒否しない。
11. The work-branch-flow shall 拒否の回数の記録を、リポジトリの管理対象に残さない。
12. When 対象の入力を受け、現在のブランチが基底ブランチである, the work-branch-flow shall 作業の開始の前に、3.3（`kiro-impl` では 3.4 を含む）と同じ内容の案内を、エージェントが受け取る指示に含める（対象の入力ごとに 1 回。通常の入力では繰り返さない）。
13. The work-branch-flow shall 現在のブランチを、フックが動く場所（セッションを始めた場所）ではなく、エージェントが実際に作業している場所を優先して判定する。操作の入力から作業場所（対象ファイルのパス、作業ディレクトリ）を求められるときはその場所のブランチを使い、直近に求められた場所を記録して、操作の入力に場所が無い場合や終了の判断にも使う。求められないときだけ、フックが動く場所のブランチを使う。

### Requirement 4: 検証後の PR 作成の案内

**目的**：開発者として、`/kiro-validate-impl` で検証が通ったら、作業ブランチの PR が作られるようにしたい。これにより、検証済みの変更が PR という形で次の確認へ進む。

#### 受け入れ基準

1. When 検証後の PR 作成が有効であり、利用者が `kiro-validate-impl` で始まる入力（`/` と `$` の形を含む）を送る, the work-branch-flow shall エージェントが受け取る指示に、検証が GO で、作業ブランチの上にいる（基底ブランチの上ではない）場合は作業ブランチの PR を作ること、NO-GO の場合は PR を作らず結果を報告することを含める。この案内は、現在のブランチの判定によらず出す（フックが見るブランチが、エージェントの作業中のブランチと一致しない場合があるため）。
2. The work-branch-flow shall 案内に、この PR の作成が設定の既定の運用であり、利用者が事前に求めたものとして扱うことを含める。
3. The work-branch-flow shall 案内に、PR の作成を通常の操作（作業ブランチの push と PR の作成）で試みること、別の仕組みがその操作を拒否して別の手順を案内した場合はそれに従うことを含める。
4. While エージェントが基底ブランチの上にいる, the work-branch-flow shall 案内の中で PR の作成を求めない（案内の文章で条件を示す。フックが基底ブランチと判定した場合でも案内自体は省かない）。
5. The work-branch-flow shall PR のタイトルと本文を、エージェントが作業の内容から作ることを前提とし、固定の文章を強制しない。

### Requirement 5: PR を作らないままの終了の停止

**目的**：開発者として、検証の後に PR を作らないまま作業が終わることを避けたい。これにより、作り忘れを 1 回の確認で防げる。

#### 受け入れ基準

1. While 検証後の PR 作成が有効であり、同じセッションで `kiro-validate-impl` の入力があり、3.13 の判定による現在のブランチが基底ブランチではなく（基底ブランチと判定された場合、および作業場所を一度も求められずフックが動く場所が基底ブランチの場合は止めない。この場合は案内だけに頼る）、そのブランチの PR が存在しない, when エージェントが応答を終えようとする, the work-branch-flow shall 1 回だけ終了を止め、PR を作るか、NO-GO などで作らない理由を示してから終えるよう伝える。
2. When 1 回止めた後にエージェントが再び応答を終えようとする, the work-branch-flow shall 終了を止めずに通す。
3. If そのブランチの PR の有無を判定できない（PR の確認に使う道具が無い、認証されていない、GitHub 以外のリモートである、など）, then the work-branch-flow shall 終了を止めずに通す。
4. While そのブランチの PR が既に存在する, the work-branch-flow shall 終了を止めない。
5. While 同じセッションに `kiro-validate-impl` の入力が無い, the work-branch-flow shall 終了を止めない。
6. The work-branch-flow shall 終了を止めたかどうかの記録を、リポジトリの管理対象に残さない。

### Requirement 6: 運用の区画の文章

**目的**：開発者として、自然文の依頼や、フックが働かない環境でも、2 つの運用フローが案内されるようにしたい。これにより、機械的な強制が効かない場合でもエージェントが同じ運用に従える。

#### 受け入れ基準

1. The work-branch-flow shall CLAUDE.md と AGENTS.md の末尾に書き足す運用の区画の文章に、新機能追加系の作業の前に作業用ブランチへ移ること、`/kiro-validate-impl` の GO の後に作業ブランチの PR を作ることを含める。
2. The work-branch-flow shall 運用の区画の文章に、2 つのフローが設定ファイルで無効にできること、既定は有効であることを含める。
3. The work-branch-flow shall 運用の区画の文章に、ブランチや PR の作成を別の仕組みが拒否して別の手順を案内した場合はそれに従うことを含める。
4. The work-branch-flow shall 同じ内容の文章を Claude Code 向けと Codex 向けの両方に置く。
5. The work-branch-flow shall 運用の区画の文章に、特定の別の仕組みの名前や宣言ファイルの名前を含めない。

### Requirement 7: 両ツールへの適用と他の仕組みとの併存

**目的**：開発者として、Claude Code と Codex のどちらを指揮役にしても同じ運用を得たい。また、既存の拒否や案内と競合しないようにしたい。

#### 受け入れ基準

1. The work-branch-flow shall Claude Code と Codex の両方に、同じ規則で作業前のブランチ確保と終了時の停止を適用する。
2. When work-branch-flow の拒否と kiro-gate の拒否が同じ操作に重なって片方の理由しか届かない, the work-branch-flow shall 入力時の案内（3.12）と、後続の操作での再度の拒否（3.5）によって、自分の案内が最終的にエージェントに届くようにする。
3. When 別の仕組みが、work-branch-flow が通した操作を拒否する, the work-branch-flow shall その拒否を取り消さない。
4. While Codex のフックの信頼が承認されていない, the work-branch-flow shall 機械的な強制が働かないことを許容し、運用の区画の文章で同じ運用を促す。
5. If work-branch-flow のフックが入力を解釈できない、または内部で失敗する, then the work-branch-flow shall 作業を止めずに通す。
