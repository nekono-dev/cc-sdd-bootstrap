# 実装計画: visible-stop

> 実機検証が必要な spec のため、実際の配置物を使う確認（1.3）を、最初の実装タスク群（1）の最後に置く。導入のフック（2）・文章の更新（3）は、1.3 で停止の出力が両ツールで成り立つことを確かめてから行う。

- [ ] 1. 停止の出力の部品と、実現性の関門の最小の形を通す

- [x] 1.1 停止の案内と止める指示を作る純粋な部品を足し、配布物に加える
  - 停止の案内と止める指示の追加の文脈を作る部品と、フックの標準出力に書く JSON を作る部品を、新しい 1 ファイルとして足す。入出力・時刻・環境変数を使わない
  - 文脈の構成: 見出し（`【入力の停止】`）、止める指示（ほかの作業をしない・停止の案内をそのまま伝えて終える・手順書に従った作業や他の案内より停止を優先する）、`--- 停止の案内 ---` の区切りに続けて、止めた入力（先頭 200 文字まで。制御文字は除く。取得できなければ「取得できませんでした」）、止めたこと、理由と次にやること
  - 出力に `decision` を含めない。理由の文面は呼び出し側の既存の文面をそのまま入れる
  - 新しいファイルを、配置するファイルの一覧とパッケージの内容に加え、配置の仕組みは変えない
  - 部品の単体テストを足す: 見出し・止める指示・止めた入力・理由が含まれること、入力が取得できない場合、長い入力と制御文字の扱い、`decision` が無いこと、同じ入力に並ぶ他の案内より優先する旨を含むこと。配置の一覧とパッケージの内容が一致することを確かめる既存のテストを成功させる
  - 完了の状態: 部品の単体テストと、配布物・配置の一覧のテストが成功する
  - _Requirements: 1.2, 1.3, 1.4, 1.5, 1.6, 2.2, 2.3, 7.1, 7.2, 7.3, 8.3, 8.5_

- [x] 1.2 実現性の関門の止める出力を、停止の案内の形に切り替える
  - 止める判定のとき、`decision: "block"` の代わりに、1.1 の部品で作った停止の案内の出力を標準出力に書く（入力の `prompt` と、既存の理由の文面を渡す）。止めない入力・止める条件・フック自体の失敗時に入力を通す扱いは変えない
  - 試験の土台が配置物を明示的にコピーしているため、新しいファイルを加える。`decision`・`reason` を直接見ている既存の確認を、停止の案内（止めた入力・理由）が追加の文脈に含まれ、`decision` が無いことの確認に置き換える
  - 複数の spec 名と `-y` を含む入力（`/kiro-spec-tasks A B -y`、A の記録が無い）、`/kiro-spec-quick`・`/kiro-spec-batch`、タスク計画が未通過の `/kiro-impl` の各停止で、停止の案内の出力になることを確かめる。記録が無い導入前の spec の案内に、記録を作る手順と不要判定の手順が含まれることを確かめる。止めない入力では何も出さないことも確かめる
  - 完了の状態: 実現性の関門のテストが新しい出力の形で成功し、止める条件を確かめる既存の判定のテストも成功する

- [ ] 2. 導入のフックの止める出力を、停止の案内の形に切り替える

- [x] 2.1 導入のフックの止める 8 か所を、停止の案内の出力にする
  - 導入の失敗（判定、書き直し後の再判定）、導入中（判定、書き直し後の再判定）、導入中の例外、区画の書き直しの失敗、導入の失敗の例外、判定不能の例外の 8 か所を、1 つの補助にまとめて、停止の案内の出力を書くようにする。入力の解析に成功した後は、元の入力（`prompt`）を関数の外の変数に保持し、後続の例外でも停止の案内に入れる。解析自体に失敗した場合は「取得できませんでした」とする
  - 理由の文面（再試行のコマンド・導入中の印の扱いなど）は既存の文面をそのまま使う。止める条件・導入済みの入力の案内は変えない
  - 完了の状態: 導入のフックが `decision: "block"` を出さず、8 つの経路すべてで停止の案内の出力になる
