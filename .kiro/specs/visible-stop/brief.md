# Brief: visible-stop

## Problem
`/kiro-spec-quick <spec 名>` のような入力を送ったのに、画面に何も出ず、入力待ちに戻る。利用者は、止められたのか、作業中なのか、失敗したのかが分からず、別の指示を送るまで状況を知れない。

## Current State
- 実際の記録（Claude Code のリモートセッション、2026-11-26）で、原因を確認した。
  - 入力 `/kiro-spec-quick install-freshness` が、実現性の関門（feasibility-gate）の UserPromptSubmit フックに止められた（`blocked_by_hook`）。
  - 結果は「成功」扱いで、`num_turns=0`。モデルは 1 回も動かず、応答の文章は 1 件も作られなかった。
  - 止めた理由（記録が無い・どう通すか）は、システムの通知と結果の文字列に入っているだけで、リモートセッションの画面には出なかった。
  - 同じ入力が、別のセッションでも同じように無応答になっていた。
- 既存の設計は、「止めた理由は利用者に示される」ことを前提にしている（feasibility-review の記録: Claude Code で確認済み）。その確認は、手元の `claude -p`（コマンドライン）で行った。リモートセッションの画面では確かめていなかった。
- 同じ型の止め方（`decision: "block"` で入力を止め、モデルを動かさない）は 2 系統ある。
  - 実現性の関門（`feasibility-gate.mjs`）: 記録が無い・未通過のとき。
  - 導入の停止（`install-cc-sdd.mjs`）: cc-sdd の導入が未完了・実行中・判定不能・失敗のとき（複数の箇所）。
- 参考: 作業前のブランチ確保（work-branch-gate）の拒否や kiro-gate の停止は、ツールの拒否や終了の停止で、モデルが理由を受け取って話すので、同じ形では無応答にならない。Codex では、入力を止めたときの理由が出力に出ない（既存の確認済み）。

## Desired Outcome
- フックが入力を止める場面でも、利用者が必ず「止めたこと・理由・次にやること」を、応答の文章として画面で読める。無応答で入力待ちに戻らない。
- リモートセッション・コマンドライン・Codex のどれでも同じように読める。

## Approach
- **モデルに話させる**（利用者の選択）。該当する入力を `decision: "block"` で止めず、追加の文脈（`additionalContext`）で「この入力は止めている。次の理由と手順を利用者に伝え、他の作業はしないこと」を渡し、必ず応答の文章を作らせる。
- 対象は、実現性の関門と導入の停止の両方（利用者の選択）。
- 作業を止める強さは、モデルへの指示を基本とし、必要ならツールの拒否（PreToolUse）で補う。補う範囲は設計で決める。
- 利用者は「無応答を検出する仕組み」までは求めていない（範囲に入れない）。

## Scope
- **In**:
  - 実現性の関門・導入の停止の、入力を止める出力を、モデルに話させる形に変える。
  - 止めた理由と次の手順を、応答の文章で必ず届ける文面の定義。
  - 運用の区画の文章・追加の指示の、止まる条件の説明の見直し（「理由は利用者に示される」という前提の言い換え）。
  - 実機（リモートセッション・コマンドライン・Codex）での確認と、PoC 文書（`poc/<段階>_<番号>.md`、poc-records の書式）での記録。
  - 既存の spec の要件・記録のうち、「理由は利用者に示される」とする記述の見直し（feasibility-review の 5.5・8.2 など）。
- **Out**:
  - 無応答の汎用の検出（モデルが思考だけで終わる等、フック以外の原因）。
  - kiro-gate の PreToolUse 拒否・終了の停止、work-branch-gate の拒否の仕組みの変更（無応答にならないため）。
  - 実現性の記録の形・判定の語・関門の判定の条件の変更。

## Boundary Candidates
- 入力を止める出力の形（block から文脈の指示へ）。
- 止めた理由と次の手順の文面（共通の言い回し）。
- 作業の実行を防ぐ補強（ツールの拒否）の要否。

## Out of Boundary
- 関門が「どの入力を止めるか」の判定（feasibility-review・session-install が持つ）。
- cc-sdd 本体の手順書・フックの形式（Claude Code・Codex の仕様）。

## Upstream / Downstream
- **Upstream**: feasibility-review（入力の停止の要件）、session-install（導入の停止）、kiro-gate（入力の検出の規則）。
- **Downstream**: 今後の関門を足す spec（止め方の型を共有する）。

## Existing Spec Touchpoints
- **Extends**: feasibility-review（要件 5.5・5.11・8.2 の「理由を利用者に示す」）、session-install（導入が未完了のときの入力の停止）。
- **Adjacent**: kiro-gate・work-branch-flow（同じ入力に並んで文脈を出す。並んだ文脈の見え方は feasibility-review の確認済み）、poc-records（PoC 文書の書式。並行して別ブランチで進行中）。

## Constraints
- 追加の文脈は、モデルが従わない可能性がある。従わなかったときの許容と補強を設計で決める。
- 実機で確かめる前提（設計の承認の前に PoC で確認する）:
  - (a) 追加の文脈だけで、リモートセッション・コマンドライン・Codex のそれぞれで、止めた理由が応答の文章として出る（`num_turns` が 1 以上で、応答の文章がある）。
  - (b) 同じ入力に並ぶ他のフック（work-branch-gate・kiro-gate）の追加の文脈と、止める指示が両立する。
  - (c) 止める指示を受けたモデルが、手順書（kiro-spec-quick など）を読んで作業を進めずに、理由を伝えて終わる（auto モードを含む）。
- 実現性の記録は、実機検証が必要と判定し、PoC 文書で根拠を残す。
- 文書は日本語で書く。
