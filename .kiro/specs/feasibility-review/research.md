# Research & Design Decisions

## ギャップ分析（2026-11-25、`/kiro-validate-gap`）

対象: `.kiro/specs/feasibility-review/requirements.md`（8 要件）。要件は未承認だが、設計の前に分かる食い違いを先に洗い出した。実機の前提は実機検証で確認済み（記録は削除済み）。

### 1. 現状の調査

- **cc-sdd 側の関係箇所**:
  - 設計の調査は `research.md` に書かれる（`/kiro-validate-gap`・`/kiro-spec-design` が追記する）。cc-sdd のスキルが書くファイルなので、実現性の記録を同じファイルに混ぜると上書きや追記の影響を受けうる。
  - `/kiro-spec-tasks` の Step 3.5 は、独立したレビュー役に「ファイルの道筋・草案・統合の文脈」だけを渡す。指揮役への追加の文脈は、そのままでは届かない。
  - `/kiro-spec-quick`・`/kiro-spec-batch` は、要件・設計・タスクの各段階を 1 回の入力の中で続けて実行しうる（`/kiro-spec-tasks` の入力は途中に現れない）。
- **kiro-gate**: `detectCommand`（任意の `kiro-*` を取り出す）を共有できる。状態は `os.tmpdir()`。失敗時は通す側（終了コード 0）。根は「スクリプトの位置」から求める。
- **入力の停止の先例**: `install-cc-sdd.mjs` が `UserPromptSubmit` で `{"decision":"block","reason":…}` を出して止める。**停止そのものは新しい仕組みがいらない**（両ツールで実機検証済み。記録は削除済み）。
- **追加の指示の先例**: 同じ `UserPromptSubmit` の `additionalContext`（kiro-gate が使っている）。
- **子の起動のフック**: `subagent-check.mjs` が両ツールで `PreToolUse` の子の起動（Claude Code は `Agent`、Codex は `spawn_agent`）を見ている。
- **運用の区画**: `catalog.agentSections` に静的な文章を `id` ごと・ツールごとに置く。更新時に既存の導入先へ自動で届く。
- **既存の spec**: 完了済みの 5 つ（installer-core・session-install・kiro-gate・subagent-delegation・codex-hook-trust）に、実現性の記録は無い。work-branch-flow・feasibility-review 自身も、記録ができるまで同じ状態になる。

### 3. 設計に引き継ぐ制約と発見

1. **観点を渡すだけでは、使われた証拠にならない**（PoC A）。関門が見るのは「文脈を渡したか」ではなく「記録に判定があるか」にする（要件 4・5 のとおり）。記録の形は、判定の行を取り出しやすい固定の見出し・固定の行にする。
2. **記録は専用のファイルにするのが安全。** `research.md` は cc-sdd のスキルが追記・参照するため、同じファイルに置くと cc-sdd 側の更新に巻き込まれる。spec のディレクトリの専用の 1 ファイル（名前は設計で決める）が、要件 4.1・4.4 に合う。
3. **spec のディレクトリの探し方に注意。** kiro-gate は根を「スクリプトの位置」から求めるが、worktree で作業するとき（brw の運用）、spec は worktree の中にあり、セッションを始めた本体の checkout には無いことがある。本体側だけを見ると「ディレクトリが無いので通す」（要件 5.7）になり、**関門が静かに効かなくなる**。入力の `cwd` から git の根を求める、または worktree の一覧も探す必要がある。
4. **`/kiro-spec-quick`・`/kiro-spec-batch` は関門をすり抜ける。** これらは `/kiro-spec-tasks` を別の入力として受けない。要件 5 は `/kiro-spec-tasks`・`/kiro-impl` の入力だけを対象にしているため、設計の確認が通らないまま tasks まで生成されうる。**要件の解釈を決める必要がある**（下の質問）。
5. **子の依頼文の機械的な検査は Claude Code だけ。** 同じ `Agent` の起動に `subagent-check.mjs` の拒否（モデル未指定）と、実現性の観点の拒否・追記が重なる。複数のフックが同じ呼び出しに `updatedInput` や拒否を返したときの順序・合成は未確認。コードを増やさない方針に照らすと、機械的な検査は持たず、運用の区画の文章（B3）と記録の確認で足りるかを設計で判断する。
6. **入力の停止は `UserPromptSubmit` の `decision: block`**。work-branch-flow の拒否（ツール操作の拒否）と、止める時点が違う（入力の時点とツール操作の時点）ので競合しない。kiro-gate の追加の文脈とは、同じイベントに両方の出力が出る（理由が届くかは未確認）。

### 4. 実装方式の選択肢

- **A: kiro-gate を拡張する**
  - 内容: `kiro-gate.mjs` の `UserPromptSubmit` に記録の確認と追加の指示を足す。
  - 良い点: 検出と状態を再利用でき、新しいファイルが少ない。
  - 悪い点: kiro-gate の境界（先読みだけ）を越え、再検証が要る。ファイルの読み取り・解析が入り、入口が重くなる。
- **B: 新しい入口を作る（`feasibility-gate.mjs` と `-rules.mjs`）**（推奨）
  - 内容: `UserPromptSubmit` の 1 イベントだけを持つ入口。`detectCommand` を読み込み、spec 名の取り出し・記録の解析（純粋な判定）と、追加の指示・停止の出力を分ける。必要なのは 1 イベントだけ（`PreToolUse`・`Stop` は不要）。状態を持たない（記録のファイルが状態）。
  - 良い点: 境界が明確で、状態を持たないため work-branch-flow より小さい。kiro-gate に触れない。
  - 悪い点: 設定の読み取りが要る場合に自前の読み取りが増える（現状は設定の項目を足さない見込みなので影響は小さい）。
- **C: B ＋ 子の起動の検査（Claude Code のみ）**
  - 内容: B に加えて、`Agent` の `PreToolUse` で依頼文の印を検査する。
  - 良い点: Claude Code では観点が確実に届く。
  - 悪い点: Codex は同じ強制ができず、両ツールで規則が割れる（要件 8.1 の「同じ規則」に反する）。`subagent-check` との重なりも未確認。**採らない見込み。**

### 5. 労力とリスク

- **労力: S〜M**（入口と判定が 1 組、運用の区画の文章、追加の指示の文章、記録の形の定義、既存 5 spec への記録の追加）。work-branch-flow より小さい。
- **リスク: 中**。(a) spec のディレクトリの特定を誤ると関門が静かに効かなくなる（worktree）、(b) `kiro-spec-quick`・`kiro-spec-batch` が抜け道になる、(c) 観点の効き目が確かめにくい（出力の形に反映されない）、(d) 既存 spec への記録の追加を忘れると、既存の spec の再検証が止まる。

### 6. 設計での調査事項（Research Needed）

1. 記録のファイル名・形式（固定の見出し・判定の行）と、解析の規則。cc-sdd の `spec.json` を変えずに済むことの確認。
2. spec のディレクトリの特定の方法（入力の `cwd` から git の根を求める、worktree の一覧を探す）を、brw の worktree で実機（PoC）確認する。
3. 追加の指示を 1 回の入力にまとめる範囲（`/kiro-spec-requirements`・`/kiro-spec-design`・`/kiro-validate-design`・`/kiro-spec-tasks`・`/kiro-impl` のそれぞれの文）。
4. 記録の判定が「通った」と書かれたあとに、設計やタスクが変更されたときの無効化の扱い（要件 4.6 は「更新して古い結果を通ったまま残さない」を求めるが、変更の検知は求めていない）。範囲外とするか、設計で決める。
5. kiro-gate・work-branch-flow の出力と、停止・追加の文脈が同じ入力に重なったときの届き方（両ツール）。
6. 5 つの既存 spec への記録の追加を、この spec のタスクに含めるか（含めないと自己適用の直後から `/kiro-impl` が止まる）。

### 7. 要件についての確認事項（設計の前に利用者の判断が要る）

- **`/kiro-spec-quick`・`/kiro-spec-batch` の扱い**（3 の 4 点目）。次のどれにするか。
  1. これらも関門の対象にする（入力の時点で、その spec の設計の記録が無ければ止める。設計・タスクの各段階を内部で実行する性質上、途中で止められないため、入口で止める）。
  2. 対象外とし、運用の区画の文章で「実現性の確認は個別の段階のコマンドで行う」と案内する。
  3. 現状の要件のまま（抜け道を許容する）。

### 8. 他の spec との接点（再検証の引き金）

- **installer-core**: `catalog` の `hooks`・`agentSections`・`files`。設定の項目は足さない見込み。
- **kiro-gate**: `detectCommand` の公開が前提（変更なし）。
- **work-branch-flow**: 同じ `UserPromptSubmit` で別の出力を返す。共通部品の切り出しの判断を、2 つの設計で合わせる。
- **既存の 5 つの完了済み spec**: 記録の追加が要る（要件 5.4）。

## 設計の調査と判断（2026-11-25、`/kiro-spec-design`）

- **Discovery Scope**: Extension（既存の配置物の型・入力の停止の先例に沿って足す）。軽い調査で足りる。前提は実機の PoC（実機検証。記録は削除済み）で確かめた。
- **Key Findings**:
  - 追加の文脈は両ツールに届くが、手順書が決めた出力の形には反映されない。観点が使われた証拠は、文脈を渡したことではなく記録の内容に求める。
  - Codex 0.172 では子の依頼文が暗号化されてフックから読めず、追記もできない。子への観点は、両ツール共通の運用の区画の文章（親が依頼文に入れる）で担保する。
  - 入力の停止の理由は利用者に示され、モデルには届かない（Codex はモデルの応答が無い）。
  - worktree で作業すると、spec が本体の checkout に無いことがある。spec のディレクトリは、入力の `cwd` の git の根・スクリプトの位置の根・worktree の一覧の順に探す。

### 設計の判断

| 判断 | 選択 | 理由 |
|---|---|---|
| 実装方式 | 新しい入口＋判定（UserPromptSubmit だけ）。`detectCommand` は kiro-gate-rules から読み込む | 状態を持たず小さい。kiro-gate の境界を越えない。方式 C（子の依頼文の検査）は Codex で効かず規則が割れるため採らない |
| 記録の置き場所 | spec のディレクトリの専用ファイル `feasibility.md` | `research.md` は cc-sdd のスキルが追記・参照するため混ぜない。cc-sdd のファイルに印を足さない（要件 4.4） |
| 記録の形 | 固定の 3 つの節と、各節の `- 判定: <語>` の 1 行。他は自由 | フックが取り出すのは判定の語だけ。人が読める形を保ち、解析を単純にする（一般化: 段階の判定を同じ形で扱う） |
| 設定の項目 | 足さない | 要件に切り替えが無い。コードと設定を増やさない（簡素化） |
| `kiro-spec-quick`・`kiro-spec-batch` | 入力時に、spec 名が取れて spec のディレクトリがあれば設計の記録で止める | 内部で設計・タスクを続けて実行し、途中で止められないため（利用者の判断。2026-11-25）。新規で名前も説明文だけの入力は特定できず通る（要件 5.7・5.12 との整合） |
| 子のレビュー役への観点 | 機械的な検査は持たず、運用の区画の文章と追加の指示で依頼文に入れさせる。確認は記録で行う | Codex ではフックが依頼文を読めない。両ツールで同じ規則にする（要件 8.1） |
| 作るか採るか | 標準モジュールだけ。新しい依存なし | git の根・worktree の一覧は `git` を引数の配列で呼ぶだけで足りる |

### 残る未確認（実装の最初のタスクで実機確認する）
- 実際の配置物での、両ツールの入力の停止と通過後の流れ。
- kiro-gate の追加の文脈と並んで、実現性の追加の指示が両ツールで届くこと（Claude Code は PoC で確認済み。Codex は届いたかが応答からは確かめにくい）。
- 停止した入力に対して kiro-gate が作る先読みの状態が、次の入力に影響しないこと。
