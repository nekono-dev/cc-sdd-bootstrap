# Brief: feasibility-review

## Problem
仕様駆動で進めていても、要件や設計を変えなければならないほどの食い違いが、実装の段階（`/kiro-impl`）で初めて見つかることがある。その場合は実装が途中で止まり、要件・設計・タスクの承認をやり直すことになって、手戻りが大きい。

2026-11-23 の、このリポジトリでの事例は次の 3 つ。

- 実機の確認が、どの spec でもタスク計画の最後のタスクだった（kiro-gate 3.2、session-install 4.2、installer-core 7.2）。そのため、現実と突き合わせるのが最後になった。
- 設計の段階の PoC は、試験用の独自のフックで確かめていた。実際の配置物では確かめておらず、Codex が追加の文脈に必ず従うことが実装の段階で分かった。
- auto モードが子のエージェントの起動を拒否した件は、PoC でも再現しなかった（文脈によって判定が変わる）。そのため、要件 5.13・5.14 を実装中に足すことになった。

## Current State
- cc-sdd（3.1.0）の扱いは次のとおり。
  - 実装中に spec が現実と食い違ったら、そのタスクに `_Blocked:_` を付けて止める（kiro-impl の Spec Conflicts with Reality）。原因が上流の spec にあれば、その spec に戻す。
  - 「実装の前に見つける」ことは求めていない。設計の調査は文書（WebSearch）とリスクの列挙だけで、ギャップ分析は「Research Needed」と書くだけ。実際に動かして確かめる段取りは無い。
- 設計・タスクの段階にもレビューの道具がある。`/kiro-validate-design`（設計のレビュー）と、`/kiro-spec-tasks` の Step 3.5（タスク計画の健全性レビュー。独立したサブエージェント）。どちらも実現性を「確かめた根拠」までは求めない。
- 「設計の承認前に PoC で確かめる」は、このリポジトリの CLAUDE.md と roadmap の制約に書いてあるだけで、機械的には強制されない。導入先には何も伝わらない。

## Desired Outcome
- 設計とタスクの承認の前に、実現性が「推測でない根拠」（一次資料の文書か、実機の PoC）で確かめられている。確かめられていなければ次の段階へ進めない。
- 実機の確認（実際の配置物を使う確認）は、タスク計画の最初に置かれる（まず端から端まで動く最小の形を作る、ウォーキングスケルトン）。
- それでも実装中に要件・設計の変更が必要になったときは、その場で書き換えずに段階を戻す（cc-sdd の Blocked の扱いに従う）。

## Approach
cc-sdd には直接手を入れず、外側から内容と方向性を指示する（cc-sdd の小さな拡張）。2026-11-23 に利用者が選んだ。

1. **文章で定める**（運用の区画）: 設計の前提は承認前に、一次資料か実機の PoC で確かめる。実際の配置物での実機の確認は、タスク計画の最初に置く。実装中に要件・設計の変更が要るときは、書き換えずに段階を戻す。
2. **レビューの道具を外から拡張する**: `/kiro-validate-design` と `/kiro-spec-tasks`（Step 3.5 の健全性レビュー）を使うときに、実現性の観点を追加の指示として渡す。観点は「設計・タスクの各前提に、一次資料（URL・版）か実機の PoC（再実行できるスクリプトと結果）の根拠があるか。推測が混じっていないか。タスクが確実に実施できる段取りか（実機の確認が最初にあるか）」。
3. **承認時の関門で止める**: 実現性のレビューが通っていない（根拠の無い前提が残る）間は、次の段階の `/kiro-spec-tasks`・`/kiro-impl` の入力を止める。止める理由と、通すための手順を示す。

却下した案:
- 実装中に requirements.md・design.md への書き込みをフックで拒否する案。手戻りを早く見つけることには効かないため、採らなかった。
- 承認の表の記入だけを機械的に照合する案。形だけの記入になりやすい。そこで、レビューの道具による実質の確認と組み合わせる。

## Scope
- **In**:
  - 運用の区画の文章（両ツール）。
  - `/kiro-validate-design`・`/kiro-spec-tasks` を使うときに渡す実現性の観点の指示（両ツール）。
  - 実現性のレビューの結果の置き場所と形。
  - その結果に基づく `/kiro-spec-tasks`・`/kiro-impl` の入力の関門。
  - 前提を確かめる PoC。
- **Out**:
  - cc-sdd のスキルの改変・複製。
  - 自然文の依頼への機械的な強制。
  - PoC の中身の正しさの自動判定（レビューの道具に任せる）。
  - 実装中の spec の書き換えの拒否。
  - 既存の 4 つの spec の設計のやり直し。

## Boundary Candidates
- 観点の指示を渡す部分（入力の時点で `/kiro-validate-design`・`/kiro-spec-tasks` を検出して、追加の文脈を出す）。
- 結果の記録の形（spec ごとのファイルか、research.md の節か）。
- 関門（記録を読んで `/kiro-spec-tasks`・`/kiro-impl` を止める）。
- 運用の区画の文章。

## Out of Boundary
- 手順書の先読みの強制（kiro-gate）。
- cc-sdd の導入（session-install）。
- 子のエージェントのモデルの決まり（subagent-delegation）。

## Upstream / Downstream
- **Upstream**:
  - installer-core（カタログへのフック・運用の区画の登録）。
  - kiro-gate（`/kiro-*`・`$kiro-*` の検出と、入力の時点のフック。同じ時点で動く）。
  - session-install（手順書の置き場所）。
- **Downstream**: このリポジトリと skyshare での運用。以後の spec の設計・タスクの段階。

## Existing Spec Touchpoints
- **Extends**: なし。新しい境界とし、kiro-gate は先読みの強制だけに保つ。
- **Adjacent**:
  - kiro-gate（コマンドの検出の規則を共有する。重複して作らない）。
  - installer-core（カタログの agentSections・hooks）。

## Constraints
- cc-sdd に直接手を入れない。指示は外側から（追加の文脈・運用の区画・レビューへの依頼文）渡す。
- 実現性のチェックは推測を含めない。根拠は一次資料の文書か、実機の PoC に限る。
- 厳密さのためにコードを増やさない。関門は短く保つ。記録が想定の形で見つからないときにどうするか（止めるか通すか）を、要件で決めて明記する。
- 設計の承認前に PoC で確かめる前提（この spec 自身にも当てはめる）:
  - (a) 追加の文脈が `/kiro-validate-design` のレビューに反映されるか（両ツール）。
  - (b) `/kiro-spec-tasks` の Step 3.5 は、独立したサブエージェントに「ファイルの道筋と草案だけ」を渡す。そのため、指揮役への追加の文脈が子のレビュー役に届くか、届かないなら依頼文に入れさせられるか。
  - (c) 関門の停止が両ツールで効くか（session-install・kiro-gate の PoC の形を使う）。
- 両ツール（Claude Code・Codex）に同じ規則を適用する。
