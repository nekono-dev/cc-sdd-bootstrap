## Implementation Notes

- レビュー役（Codex の読み取り専用の子）の環境では一時ディレクトリを作れず `npm test` 一式を実行できない。実装者の報告に頼らず、親が書き込み可能な環境で一式と RED（対象の機能を外したときの失敗の出力）を確かめ、その実際の出力をレビューの依頼に含める（1.1 で確認）。
- worktree には `.kiro/settings`（雛形）と `.claude/skills` が無い（gitignore の導入物）。手順書や雛形は本体の checkout の `/home/ubuntu/git/nekono-dev/cc-sdd-bootstrap/` から読む。
- 2.1 のレビューは、1 回目の指摘（表にないイベントの判定が継承プロパティを拾う）を修正して再確認した。2 回目の判定は REJECTED だったが、理由は読み取り専用の環境で試験一式を実行できないことだけで、指摘の箇所の修正は確認済みだった。親が書き込み可能な環境で一式（387 件中 386 成功・1 スキップ・0 失敗）を実行して確かめ、完了とした。以降のレビューの依頼には「一式を実行できない環境の制約は却下の理由にしない」を明記する。
- 2.2 は独立レビューが 5 回拒否した（毎回、別の有効な TOML の書き方で不正な TOML を `ok:true` で生成する入力が見つかった）。拒否リスト方式（既知の別表記を 1 つずつ検出）では漏れが続くため、デバッグの調査（別の提供元）の結論に従い許可リスト方式に作り直した: `hooks.state` の表の本体は `trusted_hash`・`trusted_content_hash`・`enabled` の 3 キーだけを厳格な値の形で許し、対象外の表は字句解析（文字列・コメント・括弧の深さ）で見出しだけを検出して本体は検証せず、本文全体の複数行の文字列と制御文字（タブ以外）は拒否する。改行コードは最初の改行に統一し、末尾の改行の有無を保つ。出力の妥当性は Python の `tomllib`（使えない環境ではスキップ）で試験する。
- 2.3 の取り除きは、2.2 の許可リストの検査（`findUnsafeForm` など）と改行の扱いを同じ部品で使い、取り除くときも同じ安全の検査を通す。
- レビューの依頼には、環境の制約の注意に加えて『重大度の高い不正な出力の生成が新しく見つかった場合だけ拒否、好みや範囲外は FYI』を明記すると、拒否の繰り返しを減らせる（2.2 の 5 回目の依頼で有効だった）。
- 2.3: 取り除きは、表の本体が `trusted_hash` の行と空行だけのときに限り表ごと外す（コメントや他の記録の行があれば表を残して `trusted_hash` の行だけ外す。利用者のコメントを失わないため）。ハッシュが一致しない記録は残す。write と同じ安全の検査（`prepareEdit`）を共用する。
- 2.4: 結果の形（TrustResult）は `{ status, configPath, counts, reason, notes }`、`status` は written・unchanged・removed・skipped・failed・disabled。`messageTrust(result)` は行の配列、`trustIsEffective(result)` は written・unchanged のとき true（導入コマンドが『信頼の承認が必要です』の案内を出すかの判定に使う）。3.1 以降の `codex-trust.mjs` はこの形で結果を返す。
- 3.1: `codex-trust.mjs` の `resolveHooksTarget(repoRoot)` は 3.2 で本体の checkout の特定に差し替える入口（今は `repoRoot` 直下の `.codex/hooks.json` と空の notes）。`hooks.json` が無い・自分のフックが無いときは `skipped`（設計の Error Handling の表をこれに合わせた）。`applyCodexTrust` の `beforeCommit` は試験用の差し込み口で、呼び出し側（導入コマンド・準備スクリプト）は使わない。
- 3.2: `applyCodexTrust` / `resolveHooksTarget` は、呼び出し側が git の最上位（`repoRoot`）を渡す前提。サブディレクトリを渡すと worktree 扱いになりうる（導入コマンドは最上位を要求し、準備スクリプトは自分の位置から最上位を求めるので、実際には起きない）。git が 2.31 より古いと本体を特定できず、実体の道筋で動く（エラーにしない）。
- 4.2: `delegate.mjs` は `codex-trust.mjs`（と、それが読む `codex-trust-rules.mjs`）を import する。これらの配置物を `lib/catalog.mjs` の配置一覧と `package.json` の `files` に登録するまで（4.5）、導入先では `delegate.mjs` が動かない。5.1 の自己適用の前に必ず 4.5 を済ませる。
- 4.3: `test/helpers/entry-harness.mjs` の `isolatedEnv(repo, extra)` は `CODEX_HOME`・`HOME` を必ず一時ディレクトリにする。`install-cc-sdd.mjs` を起動する試験は必ずこれを通す（通さないと、導入後の承認の記録の書き込みが利用者の実際の `~/.codex` に及びうる）。ほかの試験（`cli`・`cli.e2e` など、4.4 以降で導入コマンドから承認の段階を呼ぶもの）も同じ分離を使うこと。
- 4.4: `lib/cli.mjs` が配置物（`codex-trust.mjs`・`codex-trust-rules.mjs`）を静的に import するため、配布の登録（`lib/catalog.mjs` の `files`・`package.json` の `files`・それを確かめる試験）は 4.5 から 4.4 に前倒しした（タスク計画の抜け。登録が無いと、展開した配布物から導入コマンドが起動できない）。4.5 に残るのは運用の区画の文章の更新だけ。導入コマンドを実行する試験は、`CODEX_HOME`・`HOME` を一時ディレクトリにする分離を必ず使う（`io.env`・`io.home` で差し込む）。
