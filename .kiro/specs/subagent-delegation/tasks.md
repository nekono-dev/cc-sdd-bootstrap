- [ ] 1. 設定の項目と役割の規則（純粋）
- [ ] 1.1 設定の項目定義を役割表に置き換える
  - 旧項目（役割ごとのモデルの対応、Codex を使うかどうか）を外し、役割表の項目（既定は空）を足す
  - 役割表の検証で、指揮役の提供元・役割の名前、同じ・別、推論量（medium・high）、権限（書き込み可・読み取り専用）、格の正の整数、空でないモデルの名前を確かめ、問題の項目の道筋を返す
  - 単体試験で、正しい役割表が通り、知らない役割・不正な権限・推論量・格で問題の道筋つきの誤りになり、旧項目が既存の設定にあっても使わない項目として残ることが確かめられる
  - 同じ設定の項目定義を変える session-install 1.1 の後に行う
  - _Depends: installer-core 5.1, session-install 1.1_
  - _Requirements: 1.1, 1.8_
- [ ] 1.2 役割の解決とモデルの系統・格の規則を作る
  - 既定の役割表（指揮役の提供元ごと、要件の表のとおり。モデルは系統の名前）と既定の格を持ち、設定の明示値を既定値で置き換えずに使う
  - モデルの名前から系統を求め（長い語を先に照合）、系統から提供元を求め、子と指揮役の格を比べる（上・同じ系統・問題なし・確認できない）
  - 指揮役のモデルが分かり格 2 でないとき、明示されていない役割のモデルを要件の規則（実装は同じ提供元で 1 つ下、レビュー・デバッグは別の提供元で指揮役以下の最上位、調査は別の提供元の格 1）で決め、最下位の指揮役の実装は自分で行う扱いにする
  - 起動の名前を、設定の明示値 → Claude Code は別名 → Codex はモデルの一覧のうち系統に合う最新、の順で求め、求められなければ理由を返す
  - 単体試験で、両ツールの指揮役で要件の表どおりの役割が出ること、指揮役ごとに同じ役割へ別の推論量を設定できること、Opus・Haiku の指揮役の既定、版の違う名前（`gpt-6.1-sol`・`gpt-6.2-sol`）が同じ系統になること、一覧の最新の選択と明示値の優先、一覧が無いときの理由が確かめられる
  - _Depends: 1.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.7, 1.9_
- [ ] 1.3 子の起動の判定と拒否の文言を作る
  - 子のモデルが無い・引き継ぎなら拒否、同じ系統・上の格と確かめられれば拒否、確認できなければ通す判定を作る
  - 拒否の理由に、理由の種類と、指揮役と異なり指揮役の格以下のモデルを明示する必要を入れる
  - 単体試験で、各拒否の場合と、指揮役が不明で子が明示なら通すこと、文言の中身が確かめられる
  - _Requirements: 3.2, 3.3, 3.4, 3.6, 3.7_
- [ ] 1.4 役割定義の中身を作る
  - 提供元ごとに、その提供元が指揮役のときの役割表だけから、役割ごとに 1 つの定義を作る。同じ提供元が受け持つ役割はモデル・推論量・権限を書き、別の提供元が受け持つ役割はモデルを書かない予備の定義にする
  - Claude Code の定義は読み取り専用の役割に道具の制限を付ける。Codex の定義は書き込み可の役割だけ作り、モデルを書かない。読み取り専用の役割は作らず、適用できない旨の知らせを返す
  - 単体試験で、Claude Code の 4 つの定義の中身、Codex の定義が実装だけでモデルを持たないこと、知らせが出ること、両指揮役の設定がぶつからないことが確かめられる
  - _Requirements: 2.1, 2.2, 2.3_
- [ ] 1.5 別の提供元の CLI の引数を作る
  - Codex は承認なし・権限（読み取り専用・作業場所への書き込み）・モデル・推論量・作業場所・標準入力からの指示の引数、Claude Code は非対話・モデル・推論量と、読み取り専用なら読み取りの道具だけ、書き込み可なら編集の自動承認とシェルの許可の引数を組み立てる
  - 単体試験で、両方向・両権限の引数が確かめられる
  - _Requirements: 4.2, 4.4, 4.5_

- [ ] 2. 入口
- [ ] 2.1 (P) 子の起動を確かめるフックを作る
  - Claude Code の子の起動と、Codex の子の起動（ツール名に spawn_agent を含むもの）だけを見る
  - 子のモデルを、操作の入力のモデル → 役割の名前で指した定義ファイル（Claude Code の frontmatter、Codex の TOML）のモデル → 無ければ未指定、の順に求める。指揮役のモデルは、Codex は入力のモデル、Claude Code は会話の記録の最後の応答から読み、読めなければ不明とする
  - 拒否のときだけ拒否の出力を返し、許可の出力は出さない。設定が読めなければ既定の格で判定を続け、予期しない誤りは標準エラーに出して通す
  - 標準入力の JSON・一時の会話の記録・一時の定義ファイルを使う試験で、定義のモデルで通る・定義が無いと拒否・定義の引き継ぎは拒否・会話の記録が無く子が明示なら通す・Codex の入力のモデルで比べる・通すときに何も出さないことが確かめられる
  - _Boundary: Check_
  - _Depends: 1.3_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8_
- [ ] 2.2 (P) 別の提供元の入口を作る
  - 指揮役の提供元・役割・指示のファイルと、任意の推論量・モデル・指揮役のモデル・同じ提供元の指定を受け取り、設定を読んで役割を解決する。同じ提供元が受け持つ役割は、同じ提供元の指定が無ければ起動しない
  - 委任先が Codex ならモデルの一覧を得て起動の名前を求める。指揮役のモデルがあれば上の格・同じ系統を止める。名前だけを求める指定では、子を起動せず起動の名前と推論量を 1 行で出す
  - 指示のファイルを標準入力に渡し作業場所を根にして CLI を起動し、子の出力をそのまま流し、子の終了コードを返して最後に成否の 1 行を出す。役割が未定義・指示のファイルが読めない・CLI を起動できない・上の格・解決できない設定では理由を出して終了 2 にし、別の条件でやり直さない
  - 偽の `codex`・`claude` を置いた試験で、両方向・両権限で渡された引数・標準入力・作業場所、終了コードの受け渡し、終了 2 の各場合で CLI が呼ばれないこと、名前だけを求める指定の出力（Astra の指揮役の Codex の実装で Sol の最新、Sonnet の指揮役で Luna の最新）が確かめられる
  - _Boundary: Delegate_
  - _Depends: 1.2, 1.5_
