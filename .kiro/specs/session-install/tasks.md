## Implementation Notes
- 1.1: 設定の項目定義を `.agent-hooks/` へ移したので、配布物の `package.json` の `files` にも移した `config-schema.mjs` を同時に足す必要がある（足さないと、配布物の中で `lib/config-schema.mjs` の公開し直しが壊れる）。5.1 で `files` を差し替えるときは、この 1 行を残す。
- 製造工程の運用（2026-11-19、利用者の指示）: 実装は、まずローカル LLM（MCP の `qwen3.8:27b`）に依頼する。ローカル LLM はファイルを読み書きできないため、必要なコードを依頼文に入れ、返ってきた全文を親が配置する。レビューは Codex（Sol・読み取り専用）に送る。使い物にならない（指示から外れる・直しが 2 回続かない）場合は Codex（Luna）に戻す。1.1 は、試験と関数が仕様どおりに 1 回で返った。
- 運用（1.2 で判明）: ローカル LLM は 1 回の返答が長いと途中で切れる。依頼は「試験」と「実装」に分け、1 回の出力を小さく保つ。レビューの依頼文には、実装前の試験の失敗の出力（RED_PHASE_OUTPUT）を最初から含める（無いと、コードに問題がなくても不採用になる）。実装前の失敗は、`git stash` ではなく、HEAD の版を一時ディレクトリへ写して取る（仮追加のファイルがあると stash が失敗する）。
- 1.2: 設定の項目を足すと、設定の項目の一覧・補い・init の設定ファイルの中身を固定で書いた既存の試験の期待値が変わる（`test/config.test.mjs`・`test/cli.e2e.test.mjs`）。以後に項目を足すタスクがあれば同じ更新が要る。
- 運用（2.1 で判明）: Codex のレビューは、全体の試験を実行させると 9 分で時間切れになることがある。依頼文には、読む差分のファイルと、実行してよい試験のファイルを限り、「8 分以内に判定を返す」と書く。ローカル LLM の返答が長くなるときは、依頼を「試験の前半・後半」「実装」に分け、コメント不要・短く、と指示する（それで切れずに届いた）。
- 2.1: `lib/catalog.mjs` の `CatalogGitignoreLine` は、`when.equals` の型を設計どおり `ConfigValue` にしてある。5.1 でカタログの中身を差し替えるときも、この型に従う。
- 運用（3.2 で判明）: Codex の読み取り専用の環境では、一時ディレクトリを作る・子のプロセスを動かす試験を実行できず、レビューが「検証未成立」で不採用になることがある。依頼文には、親が実行した試験の成功の出力を参考として添え、`TMPDIR` を書き込める場所に変えた実行の指示を入れる。それでも実行できない場合は、読解での判定を許す（レビュー担当が実行不能の事実を書いたうえでの承認）。完了の確認は、親が全体の試験を実行して行う。
- 3.2: 記録のファイルが存在するのに読めないとき、停止の処理は「読めなかった旨を詳細にして止める」。要件 3.5 に合い、3.8（停止の判定そのものが行えない）には当たらないと、レビューで確認した。
- 3.2: 停止の処理が示す再試行のコマンド（`node .agent-hooks/cc-sdd-bootstrap/install-cc-sdd.mjs`）は、判定側の定数 `RETRY_COMMAND`（3.3・3.4）と同じ文字列でなければならない。一致は 4.3 の通しの試験で確かめる。
- 製造工程の切り替え（3.3、2026-11-19）: ローカル LLM は、返答の途中切れ（約 2,000 トークン）が 4 回、実装の不具合が 1 回（2.1）、試験の論理の誤りが 1 回（3.3）あり、規模が大きくなる 3.3 以降は使い物にならないと判断し、Codex（Luna・workspace-write）に戻した。依頼文は、タスクの原文・これまでの実装メモ・触ってよいファイルを入れ、`## Status Report` の形で返させる。結果は未確認として扱い、親が差分と全体の試験で確かめてからレビューに回す。ローカル LLM が向く範囲は、1 回の出力が 1,500 トークン以下に収まる小さな関数と試験。
- 4.1: Codex（Luna）の環境は、子のプロセスを動かせない（`EPERM`）・一時ディレクトリを作れない（レビュー担当は `EROFS`）ため、子のプロセスを動かす試験（4.1〜4.4・5.2 の通しの試験）は、実装担当・レビュー担当のどちらも実行できない。実装担当には試験の作成と実装までを頼み、親が実行して確かめる（実装担当が確かめられなかった箇所のバグは親が直す）。レビューは、親の実行結果の出力を添え、読解での判断を許す。
