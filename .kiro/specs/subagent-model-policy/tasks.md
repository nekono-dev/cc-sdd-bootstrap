  - フックの振り分けに、委任入口の呼び出しの書き換えと拒否を接続する。入口の決まった形（操作ごとに固定した引数、各引数 1 回まで、必須の引数がすべてある、値は安全な語か引用符を含まない一重引用符の文字列）の呼び出しに限り、現在のセッション・ターンの参照を付け足した命令に組み立て直して実行させる。入口の道筋はフックが自分の配置場所から求め、呼び出し時の作業ディレクトリに依存させない。

- 4.4・4.5 の本物の入口での確認は、下流 codex-delegation の委任入口が新しい参照の種類（開始・制御）と引数の指紋を消費できること（同仕様のタスク 5.2）に依存する。入口側が未対応の間は、フックの単体・統合試験までを本仕様で完了し、実機の通し確認は下流の実装後に 4.4・4.5 として行う（本仕様の `_Blocked:_` ではなく、下流のタスク 6.1 と合わせて実施する）。
- 4.2 と 4.3 の前提は、承認済み設計と設計時の PoC で使用したクライアント、認証、一時リポジトリを作成できる環境。1.1 で実行環境と既存 PoC の入口を確認する。

- 1.1 を確認した環境は Node.js 22.16.0、Claude Code 2.1.329、Codex CLI 0.167.0。独立した実行環境で両クライアントの実機 PoC と模擬 API が成功した。委任エージェントの子プロセスではネットワークまたはループバックが制限されるため、実機の再検証は親が行う。
- 2.3 のフック境界では、ホストの `PreToolUse` が呼び出し ID を記録し、固定コマンドに参照を渡す。入口は実際の作業先と引数の参照から記録を解決する。Codex は公開ターン ID を必須とし、Claude Code はプロンプト ID がない場合に内部世代を使う。正規手順の読み取り成功と、明示入口での参照消費はそれぞれ開始経路となる。
- 2.4 の単独発行は設定・配置台帳・対象定義を照合する。共有経路も発行と消費の両方で現在の設定を確認し、対象外クライアントを拒否する。通常作業の判定では状態を置換しない。
- 2.5 はモデル切替前に観測記録の世代を無効にする。観測保存に失敗した場合も別プロセスが古いモデルを使わないことを検証した。切替の失効処理に失敗したときは、3.2 のフックで切替を拒否する。
- 2.6 は実機で確認した `sandbox_policy.type`、`permission_profile.file_system`、同一ターンの作業先を照合する。製造役の発行と消費、発行後の権限変更による拒否を模擬入力で確認した。
- 3.1 は対話完了後の設定と台帳に基づいて生成先を確定する。配布物からの導入・削除と、作業ツリーの再更新で差分が出ないことを確認した。
- 3.2 の自動試行で残った統合入口は手動で接続し、独立レビューで確認した。フックが参照を消費し、シェルには結果表示だけを渡す。Claude Code の書き込み役はホストから権限の隔離を証明できない場合に拒否する。
- 4.1 は一時リポジトリと配布物で導入、旧設定の移行、切り替え、削除を確認した。両クライアントへの切り替えで明示した全設定を保持し、競合時には対象ファイルを変更しない。
- 4.2 は認証済み Claude Code で正規 Read、モデル切替後のレビュー起動、直接起動・再使用・証拠不足の拒否、通常起動を確認した。実クライアントの API リクエストを模擬 API で照合し、推論量と読み取りツールを確認した。
- 4.3 は認証済み Codex 0.167.0 の V1 で、管理起動、子の Sol・high・read-only、再使用拒否、子の終了後の再発行、同一セッションの通常起動を確認した。子イベントは親と同じ session_id を使うため agent_id で状態を分けた。V2 の暗号化された依頼本文は事前確認と一致を証明できず、本仕様の管理起動は拒否する。
- 実装全体の再検証で、Claude Code の強制モデル・推論量上書きが一致しないか不明な場合を拒否するようにした。模擬 API を使った実クライアントの検証と全体テストで確認し、14タスクすべてと実装ゲートが完了した。
- 2.3（改訂）は、参照の記録に入口の種類・参照を除いた引数の指紋を持たせ、消費時に照合する。永続記録に依頼本文（`toolUseInput` の `prompt` など）を残さない。`delegate-control` の消費結果は照合済みの対象手順を返し、管理状態（`active`・`skill`）は変えない。公開入口（`handleEntryArgv` ほか）は、正規表現へ渡す前に引数の型を検証する。レビューで 3 回差し戻され、デバッグ担当の修正計画で解決した。
- 2.4（改訂）の単独発行は、有効な外部候補の有無で判定する（導入台帳の委任入口の有無は見ない）。候補を求める処理の失敗（未知キーなど設定の不正）は、正常な「候補なし」と区別して発行を拒否する。さもないと不正な設定を足すだけで管理入口の必須判定を迂回できる。
