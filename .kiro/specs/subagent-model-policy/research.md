# Research & Design Decisions

## Summary

- **Feature** — `subagent-model-policy`
- **Discovery Scope** — 既存導入基盤への拡張と、二つのクライアントに対する起動フックの実機確認。
- **Key Findings** — 既存の文字列マップ形式は再利用できる。子エージェントの起動・拒否は両クライアントで観測できる。指揮役モデルと権限の取得方法はクライアントごとに異なる。

## Research Log

### Claude Code 2.1.329

- `PreToolUse(Agent)` に `subagent_type` が入り、拒否を返すと子の開始イベントと子モデルの利用が発生しなかった。許可した試験では親が Sonnet、定義で指定した子が Haiku になった。
- `SessionStart` と最初の `PreToolUse` ではモデル欄が空だった。最初のフックで会話記録のモデルを読めない例もあった。毎回会話記録の最後の値から判断する案は、初回や切り替えの競合を扱えない。
- 入力のストリームでモデルを切り替えると `PreModelSwitch` と `PostModelSwitch` に正規 ID の `from_model` / `to_model` が入り、次の応答は Haiku になった。公式資料では対話の `/model` も同じイベントを使う。
- 定義の `effort` は公式にサポートされ、呼び出し時の値、環境変数が上書きし得る。模擬 API へ接続した実機のリクエストを観測し、親 Sonnet は `medium`、子 Haiku は定義どおり `high` が送られることを確認した。

### Codex CLI 0.167.0

- 信頼済みの隔離プロジェクトで broad matcher を使い、実機の `PreToolUse` に `collaborationspawn_agent`、親モデル、子の `agent_type` が入る経路を確認した。フックの拒否理由は親に届き、子は起動しなかった。公開資料とタグ付きソースは別経路の `spawn_agent` と `Agent` も示すため、対象環境で両方を識別する。
- 履歴を引き継がせた試験では、役割名が送られても子が親と同じ Sol になった。引き継ぎを明示的に無効にし、Luna と `high` を指定した試験では子の記録に Luna、`high`、読み取り専用が出た。
- 読み取り専用の試験でもフックの `permission_mode` は `bypassPermissions` だった。フックの `turn_id` に対応する会話記録は読み取り専用の `sandbox_policy` と権限プロファイルを示した。権限は対応するターンの記録で確かめる。

### installer-core と既存配置

- `.cc-sdd-bootstrap.json` の `models` と `codex.enabled` は既に存在する。既存のモデル指定を保持し、クライアント別設定を追加する。
- 現行のカタログは同梱の固定ファイルを管理ディレクトリへ写す。ネイティブ定義は設定で内容が変わるため、生成物の予約パスと配置記録を結びつける必要がある。既存の設定・フック・管理区画の統合と、競合時の動作を再利用する。

## Design Decisions

| 選択肢 | 判断 |
|---|---|
| クライアントごとに役割やモデル選択を複製 | 外部委任とネイティブ起動の条件がずれるため、共通の役割解決を採用する。 |
| フックでモデルと推論量を毎回書き換える | 有効な引数と上書き順が異なるため、管理対象の定義を生成し、フックで起動の適格性を確認する。 |
| 最後に記録された指揮役モデルを常に使う | 最初の起動やモデル変更の直後に古い判定を使う危険がある。イベントまたは当該ターンの確定情報が得られない場合はネイティブ起動を拒否する。 |
| Codex の定義に子専用サンドボックスを指定 | 親の権限が引き継がれるため、必要権限と現在の親の権限を照合する。 |

## 委任ガードの改訂判断

- 2026-11-21 の確認で、事前確認の強制は cc-sdd 作業中に限ると決定した。プロジェクト全体に常時適用すれば識別漏れは減るが、通常作業のツール起動も制約する。採用した方式では、明示コマンドに加えて、自然文から手順利用に切り替わる入口をホストで確認する。
- kiro-gate の既存設計はスラッシュコマンドの検出を扱い、自然文の強制を対象外としている。本仕様は kiro-gate の内部状態を前提にせず、スキルの起動・読み取りイベントまたは管理入口によって作業範囲を識別する。既存の `dev/kiro-gate` の PoC では、Claude Code の開始フックに `/kiro-*` の入力が届き、読み取り完了イベントから手順書の道筋を取得できることが確認されている。
- 予約名で絞るだけでは組み込み起動が通る。管理作業中は起動ツールで一回限りの事前確認を消費し、起動引数・役割または現在の条件が一致しない場合は拒否する。

## Risks & Mitigations

- モデルの別名、利用可能な推論量、フックのイベント名は版やプロバイダーで変わる。実環境に適用できるかを確かめ、確定できない候補を起動しない。
- Codex のユーザー設定、プロジェクトの信頼とフックの承認は利用者の管理対象。PoC の抑制オプションや検証フックの信頼設定は配布時に使わない。
- クライアントの通常挙動と管理対象の起動を混同しない。所属を確認した管理対象の役割を、適合が確認できた場合だけ起動する。

## 下流の実機検証を受けた改訂（2026-11-22）

下流の codex-delegation の実機の通し検証（`poc/codex-delegation-live/result.md`）で、上流の部品に原因がある問題が 2 つ見つかった。利用者の決定（2026-11-22）により、下流の都合で上流のコードを黙って書き換えず、先に本仕様の要件と設計を改訂する。所有者を本仕様とし、上流の再検証の根拠をここに残す。

### 観測した事実

- **G1（管理入口の参照がモデルに届かない）** — `enter kiro-impl` の結果は `{"ok":true,"skill":"kiro-impl"}` だけで、参照は出ない。実装では、フックが `enter` の呼び出しを受けると、その場で参照を発行・消費して作業範囲を開始し、シェルには結果表示だけの命令（`receipt`）を渡す（`subagent-model-policy-hook.mjs` の `prepareEntry`）。一方、下流の `delegate.mjs start` は `--reference` を必須とし、`consumeReference` は記録の命令が `enter` の形であることを要求する。そのため、モデルが `delegate.mjs` に渡せる参照は存在しない。
- **G3（ネイティブ単独の事前確認が常に拒否される）** — `preflight` は「外部委任の配置を検出したため単独発行できません」で拒否された。外部 MCP を置かない構成でも同じ。原因は `verifyStandaloneInstall` が導入台帳の `.agent-hooks/cc-sdd-bootstrap/delegate.mjs` の有無（と実体の有無）で拒否すること。現行の導入は `delegate.mjs` を常に配置する。
- **Codex の Bash の書き換え** — Codex CLI 0.167.0 の PreToolUse で、シェルの `tool_name` は `Bash`、`tool_input.command` が文字列で届いた。`permissionDecision: "allow"` と `updatedInput` を返すと、書き換え後の命令が実行された（実行ログの `command` で確認。2 回とも同じ）。未確認は、実際の `delegate.mjs` の命令での成立と、書き換え後の命令がモデルに見えないこと。

### 判断

| 選択肢 | 判断 |
|---|---|
| G1: `enter` の出力に参照を載せる | 採らない。一回限りの秘密がモデルの文脈と会話記録に残り、モデルが書いた参照と区別できなくなる |
| G1: フックが `delegate.mjs` の決まった形の呼び出しに参照を付け足す | 採用。`enter` と同じ仕組みで、参照はモデルに渡らない。両クライアントで書き換え応答が使える（Codex は実機確認済み） |
| G1: 参照なしで、フックが書いた作業コンテキストのファイルから入口が解決する | 採らない。参照の消費による偽装防止が弱まる |
| G1: 参照を元の命令の文字列に連結する | 採らない。値の引用の扱いで命令の意味が変わり得るため、解析した引数から組み立て直す |
| G3: 判定を設定の有効な外部候補に基づける | 採用。実際に外部委任を使うかを表す。設定の中身だけで判定でき、下流の配置物を読まない |
| G3: 判定をホストの登録の承認状態まで確かめる | 採らない。フックの中でホストの命令を実行することになり、遅く、失敗の扱いが増える。承認待ちでも管理入口がネイティブへ落とすため行き止まりにならない |
| G3: 判定を下流の管理委任の有効状態（`MANAGED_DELEGATION`）に結び付ける | 採らない。上流が下流の配置物を読む向きの依存になる |

### 残るリスク

- 決まった形を狭くすると、空白を含む道筋などで呼べない場合がある。一重引用符の値を受け付けることで緩和し、それでも合わない場合は拒否理由で形を示す。
- 管理入口の道筋と操作名を含む呼び出しを拒否する判定は文字列の検出に頼る。拒否にだけ使い（安全側）、作業範囲の開始には使わない。
- 参照がモデルに見えないことは、ホストが書き換え後の入力をモデルに返さないことに依存する。実機で確認するまで、そのホストで管理経路として公開しない（要件 5.7）。
