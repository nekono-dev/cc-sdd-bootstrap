# プロジェクト構成

## 構成の方針

「このリポジトリで動くもの」と「利用先へ配置するもの」を分ける。利用先へ配置するものは、このリポジトリの中でも配置後と同じ相対パスの形で持ち、導入コマンドはそれを写すだけにする（配置物の中身を導入コマンドの中で組み立てない）。

配置物は、このリポジトリでも導入先と同じ相対位置に置く。導入コマンドはカタログ（導入対象の一覧）に載った内容をそのまま写す。

## ディレクトリの型

### 入口 `bin/`
コマンドを受け取る入口を置く。引数や処理の本体はここに集めない。

### 処理 `lib/`
役割ごとに処理を分け、依存は「データ → 純粋な処理 → 入出力 → cli」の一方向にする。この矢印は右側が左側を読み込むことを表す。純粋な処理とは、ファイルを読まず書かず、入力から結果だけを計算する処理。cli（コマンド操作部）は、引数や対話を受け取り処理を呼び出す部分。

### 配置物 `.agent-hooks/<ツール名>/`
利用先へ写すファイルを置く。このリポジトリでも導入後と同じ相対位置を保つ。配置物は導入コマンドの部品を読み込まない。

導入対象のファイルを増やす下流の spec（後続の機能仕様）は、配置物を追加するほか、`lib/catalog.mjs` の一覧と `package.json` の `files` にも登録する。

### テスト `test/`
処理の小さな確認から、実際のコマンドを使う確認までを置く。

### PoC `poc/<前提ごと>/`
Claude Code など外部の動作上の前提を確かめる再実行可能な `run.sh` と、その結果を記す `result.md` を置く。

プラグインは plugin-skill によって追加する。

## 命名

- ファイル: kebab-case（`kiro-gate.mjs` など）
- 関数: camelCase。判定を返す関数は `decide…`、状態を作る関数は名詞で始める

## コードの決まり

- 配置物のスクリプトは、利用先のリポジトリのルートを自分の位置から求める（呼び出し元のカレントに依らない）。
- 配置物は導入コマンドの部品を import しない（利用先には配置物しか無いため）。
