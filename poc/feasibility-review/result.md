## 分かったこと

1. **追加の文脈は届くが、手順書が決めた出力の形には反映されなかった（A）。** 両ツールとも、レビューは行ったが指定の行は付けなかった（出力に「根拠」の語は出たが、設計の文面に「根拠は無い」とあったためで、文脈の効果とは言えない）。そのため、観点を文脈で渡すだけでは、観点が使われた確かな証拠にならない。**証拠は、レビューの結果をファイルに残させ、そのファイルを関門が確かめる形（設計で決める）にする。**
2. **Codex 0.172 では、`spawn_agent` の `message`（子への依頼文）が PreToolUse の入力に暗号化された文字列で届く（B1・B2）。** フックは依頼文を読めず、印の有無を検査できない。足す方式は暗号の検証に失敗し、子が起動しなかった（「The encrypted content … could not be verified」）。Claude Code の `Agent` の `prompt` は平文で、検査も追記もできる。
3. **文章で決める方式は両ツールで動いた（B3）。** 親が運用の決まりに従って子への依頼文へ書き入れた。ただし従うかはモデルしだいで、機械的な強制ではない。プロジェクトの方針（子が CLAUDE.md・AGENTS.md を読むことに頼らない）のとおり、親が依頼文へ入れる決まりとして書く。

## 設計に引き継ぐこと

- (b) `/kiro-spec-tasks` の Step 3.5 の子のレビュー役への届け方: Claude Code は PreToolUse で検査・追記できるが、Codex はフックで触れない。両ツール共通の方式は「運用の区画の文章（親が依頼文に入れる）」＋「レビュー結果のファイルを関門が確かめる」になる。
- (a) 文脈の反映は保証されないので、「文脈を渡した」ことではなく「実現性のレビュー結果が記録された」ことを関門の条件にする。
- 記録が想定の形で見つからないときの扱い（止めるか通すか）を要件で決める。

## 追記: 配置した入口の停止と通過（場面 C、2026-11-26、タスク 1.3）

- 実行: `node poc/feasibility-review/run.mjs C`（`cc-sdd-bootstrap init` と `install-cc-sdd.mjs` で配置・導入し、`kiro-spec-tasks`・`kiro-impl` の手順書だけを確認用に差し替える。kiro-gate・work-branch-gate も同時に動く）
- 環境: Claude Code（haiku、`--setting-sources project`）、Codex CLI（`-a never`・`-s workspace-write`・承認の省略指定）

| 入力 | 記録 | Claude Code | Codex |
|---|---|---|---|
| `kiro-spec-tasks demo` | なし | 入力が止まる（理由に spec 名・記録の場所が出る） | 入力が止まる（モデルの応答も作業も無い） |
| `kiro-spec-tasks demo` | 設計が通過 | 通る（モデルが応答） | 通る |
| `kiro-impl demo` | 設計だけ通過 | 入力が止まる | 入力が止まる |
| `kiro-impl demo` | タスク計画が通過 | 通る | 通る（作業前のブランチ確保が先に効き、`.git` が書けず止まった。この確認とは別の関門） |

事実:
1. 停止と通過は、記録の有無と判定の値のとおりに、両ツールで成立した。
2. 停止の理由は、Claude Code では出力に出る。Codex では出力に出ず、モデルの応答も作業も無い（既知の見え方）。そのため、停止の理由の文面が利用者に見えることは Codex では確認できていない。
3. 実機の試験の組み立て: 手順書の導入（`install-cc-sdd.mjs`）を先に済ませる必要がある。済ませないと、最初の入力で導入が走り、後の入力が「別のセッションで導入中」で止まる（この PoC 側の事情で、関門とは別）。
